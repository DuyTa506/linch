# WP8 hot-path baseline — 2026-10-31

This is the measured starting point for WP8 steps 1–2. The benchmark source is
`scripts/benchmark_runtime.py` at the step-1 commit. Production code is
unchanged. Each row is the median of three fresh child processes on the same
machine. The workload is the existing offline scale workload: one shared Agent,
the fake provider and RAG/SQL/save-note tools, asynchronous 2 ms provider/tool
delays, and four turns unless the case says 50 turns.

## Baseline command and environment

Memory cases:

```bash
/home/duy/Downloads/duy_dev/agent_kit/.venv/bin/python \
  scripts/benchmark_runtime.py --scale --scale-case CASE --json
```

Postgres cases use the supplied `AGENT_KIT_TEST_PG_DSN`. Every child creates a
fresh `linch_scale_<uuid>` schema before timing, runs schema initialization
outside the measured burst, and drops the schema after the run. This avoids
reading old state and keeps each sample isolated.

Machine: Intel Core i7-10750H @ 2.60 GHz, 12 logical CPUs; x86_64 Linux
6.8.0-138-generic; CPython 3.11.14; 16,163,348 KiB physical RAM.

`ms/turn` is elapsed successful-burst wall time divided by observed provider
turns. `runs/s` is successful runs divided by burst wall time. Memory “store
round trips” are the successful store mutation API calls already reported by
the baseline (there is no SQL driver). The retained step-1 Postgres samples use
`driver command calls/turn`: the sum of both stores’ instrumented asyncpg
command calls and `Connection.reset()` calls after schema setup. `execute`,
`executemany`, `fetch`, `fetchrow`, and `fetchval` each count once;
`BEGIN`/`COMMIT`/`ROLLBACK` are broken out as transaction commands, and pool
reset calls are broken out separately. Pool acquire/release counts are also
retained. This command metric includes transaction and pool-reset overhead
visible at the asyncpg connection boundary, but one command can contain
multiple protocol exchanges.

The benchmark now also reports `protocol_exchanges/turn`, an attempted
asyncpg protocol-cycle count from the connection protocol (`query`, `prepare`,
`bind_execute`, `bind_execute_many`, `execute`, and `close_statement`), with
failed attempts retained separately. It is the actual exchange metric for new
interleaved runs; the retained step-1 timing files predate this proxy and thus
have no honest protocol-exchange column. No command count is relabeled as a
wire packet count.

Checkpoint, event, and session-append bytes are UTF-8 JSON payload sizes before
the store call. Checkpoint bytes include every phase write, including terminal
writes. Event bytes use the persisted event envelope; session bytes sum each
message passed to `append_messages`. These are logical wire bytes, not disk
pages or WAL volume.

## Trace equivalence fixture

Before any `src/linch` change, the committed
`2026-10-31-wp8-trace.py` captured normalized full event traces for a text-only
success and a persistence path with two fixed read calls followed by a fixed
write call, all using an `InMemoryRunStore`. The byte-for-byte baseline is
`2026-10-31-wp8-traces-baseline.json`. Normalization removes run/session
identities and timing fields while retaining event order, phases, tool names,
fixed tool-call references, and payloads. `Agent.cwd` is explicit and fixed
across source snapshots. The current in-progress source produced an exact
normalized match against this baseline; the same fixture will be rerun after
each runtime change.

## Step-1 implementation delta

`--scale` now exposes memory and Postgres cases for 200 × 4, 1,000 × 4, and
1 × 50. Postgres cases are reported as skipped when
`AGENT_KIT_TEST_PG_DSN` (or `asyncpg`) is unavailable. The benchmark owns the
measurement wrappers; no runtime or public API names changed. The wrapper also
reports checkpoint, event, and session-append bytes separately so later steps
can show which payload changed.

## Step-2 cProfile results

Each profile ran one fresh child directly through `run_scale_case` with
`cProfile.Profile`. The profile envelope begins before `asyncio.run`, so it
includes schema creation, pool/schema setup, pool/Agent teardown and result
serialization; only the benchmark's burst timer excludes setup. These are the
original instrumented profiles: payload-byte accounting was enabled and repeats
production JSON normalization for measurement. They are useful for locating
hot paths, but not for an unbiased codec CPU ranking. The complete profile text
and `.prof` files are retained in `/tmp` while this work package is being
implemented (`/tmp/wp8-profile-*.txt` and `/tmp/wp8-profile-*.prof`). Times
below are cProfile self/cumulative seconds, so async selector wait is visible
in the Postgres rows.

The reusable profile runner now supports a lean mode that disables only the
extra payload-byte encoding (`LINCH_SCALE_PROFILE_LEAN=1`), while keeping the
same workload and all cheap counters:

```bash
/home/duy/Downloads/duy_dev/agent_kit/.venv/bin/python /tmp/profile_wp8.py \
  --lean memory 200 4 /tmp/wp8-profile-memory-200x4-lean.txt
```

Lean profiles must be run against the archived `b69d400` production source with
the committed benchmark copied over it; no lean profile is treated as a
before/after result until that source boundary is explicit. The profile files
below therefore remain labeled **instrumented** and retain the setup/teardown
scope above.

The profile points to checkpoint serialization and the JSON-safe event/checkpoint
walk (`_json_safe_inner`, `checkpoint_to_dict`, `deepcopy`) as the dominant CPU
work. Postgres additionally spends visible time in selector polling and asyncpg
I/O; it does not change the serialization finding. D15’s codec experiment should
therefore measure event/checkpoint encode/decode directly on these scale cases.
