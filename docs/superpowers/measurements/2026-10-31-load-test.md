# WP18 fleet load test

## Rebuild and validation

The maintained-tool harness replaces the exploratory Python byte proxy with
Toxiproxy 2.13.0 and replaces `/proc` parsing with psutil 7.2.2. The deployment
is one API/enqueuer process, M independent Worker processes, and dedicated
Postgres 16.2 at `127.0.0.1:55432` (300 maximum connections). Only setup,
monitoring and checks connect directly; experiment traffic uses Toxiproxy.
A fresh schema is removed after every point and all child processes are reaped.

The earlier shared-server pilot completed 21/21 runs without duplicate notes,
sequence gaps or owner mismatches. Its capacity explorations are hypotheses,
not results for the rebuilt topology: small pools filled before worker CPU,
and more workers exposed advisory-lock contention and Python-proxy saturation.

Postgres computes steady-window throughput, terminal/claim latency percentiles,
turn rate and correctness checks. A small claim audit captures actual D1 lease
claim times and epochs. A mismatch-only event trigger checks writer identity.
Client distributions (loop lag, pool use and append-to-read lag) are aggregated
in Postgres too. Workers use an offline four-turn provider with 300 ms TTFT,
20 deltas over 700 ms and RAG/SQL/save_note tools with 30–80 ms fake I/O.
Arrivals are open-loop Poisson. Configurable warmup/steady defaults are 15/60 s.

CPU uses psutil, where 100% is one logical CPU. Postgres CPU includes only the
postmaster and children serving the selected database server. Database counters
are clean deltas on the dedicated instance. Every heavy run must hold
`flock /tmp/wp8-cpu.lock`. Workers, proxy and Postgres share this 12-CPU host;
the measured fleet knee will be a lower bound for separate production hosts.

## RTT blocker — owner decision required

Installed Toxiproxy 2.13.0 accepts integer milliseconds only. The required
RTT=1 ms setting needs `latency=0.5` on each direction, which returns HTTP 400:

```text
bad request body: json: cannot unmarshal number 0.5 into Go struct field
.attributes.latency of type int64
```

This was verified against a temporary server using `POST /proxies/pg/toxics`
with `{"type":"latency","stream":"upstream","attributes":{"latency":0.5,"jitter":0}}`.
The probe server was stopped afterwards. No silent rounding was applied.
The requested capacity, network, chaos and reader-fan-in tables are pending
resolution of this setting. An asymmetric 1/0 ms RTT=1 or a symmetric 0/2/4 ms
matrix requires an explicit owner decision.

## Dependency and scope notes

`psutil>=7.2.2` was added to the dev extra. `uv lock --offline` failed because
cached distributions do not satisfy the resolver's Python >=3.14 split;
`uv.lock` remains unchanged as instructed.

Queue-pick latency is omitted; reported queue wait is enqueue to actual D1
claim. There are no per-run client sample files or client-side percentile
calculations. Experiment 4 is the network command's `--readers 100` option,
which repeats its middle point for comparison.

The capacity ramp is bounded to six geometric points per worker count. A knee
beyond that range is reported as unreached. Event errors are grouped by their
persisted name/type; `runs.meta.errors` is not separately aggregated. Reader lag
covers subscription lifetime, including warmup/drain. Default pool size is 8,
queue limit 0 (fleet-wide unlimited), lease/stall windows 4/6 s and worker polling
200 ms. These settings are flags; the dedicated server permits a larger pool
budget than the earlier shared-server exploration.
