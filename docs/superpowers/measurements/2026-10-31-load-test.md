# WP18 fleet measurements — 2026-10-31

Current acceptance results: [scale-ready gate](2026-10-31-scale-gate.md).

The latency threshold brackets are 6.5–8, 10–12, 12.5–16 and 12.5–16 offered runs/s for M=1,2,4,8. Adding workers beyond four did not raise the tested stable-rate bracket. A snapshot at M8/rate16 identified 76 backends waiting on Linch's shared schema-initialization lock. Kill recovery exposed a pre-checkpoint initialization defect, and a three-second database interruption exposed a listener-recovery defect. The resilience gate remains open.

## Method

Code under test: Linch at a10aa04, before the WP8 hot-path merge (f23d726, about 95 → 15.5 Postgres round trips per turn) and before one verified store pair per worker (498627f). The capacity numbers below are therefore a pre-WP8 baseline.

One Intel Core i7 host, six physical cores / 12 logical CPUs, hosts API, workers, proxy and dedicated Postgres 16.2 on TCP port 55432 (max_connections=300). Workers, proxy and Postgres share these CPUs, so the measured knee is a lower bound for separately provisioned production hosts. Heavy commands hold `/tmp/wp8-cpu.lock`.

Each point uses an isolated schema, one API/enqueuer process and M worker processes, independent pools of 16, and fleet-wide queue concurrency C=0 (unlimited). Pool 16 is a measurement setting; the CLI default remains eight. Warmup is 15 s, steady 60 s, followed by bounded drain. Arrivals are open-loop Poisson. Unloaded rate-two baselines use zero readers; loaded points use one witness reader. These single samples do not eliminate Poisson variation or provide confidence intervals.

Toxiproxy 2.13.0 adds integer RTT 0/1/2 ms upstream and zero downstream: this shifts one-way timing while preserving request/response round-trip cost; only setup, monitoring and audit bypass it.

The offline provider derives its four turns from assistant history: RAG, SQL, save_note, then final text. Each call has 300 ms TTFT and 20 deltas over 700 ms; tools add 30–80 ms simulated I/O. Read tools are read-scoped; save_note is write-scoped with a unique run/tool-call receipt and explicit attempt counter.

Postgres computes run distributions and correctness over every durable run, including ambiguous enqueue commits. Latency follows steady-arrival runs through drain, from enqueue start to terminal-status timestamp; throughput counts successful terminal timestamps inside steady. D1 wait is enqueue to first actual lease claim, recorded by a small trigger; queue-pick latency is omitted. Run/event timestamps precede commit and are not commit-clock measurements. A mismatch-only trigger compares event writer identity with active owner.

psutil measures each worker, the Go proxy and the selected Postgres postmaster plus its children. CPU 100% means one logical core; Postgres/Go may exceed 100%. Database commit/inserted-row/WAL deltas use actual sample elapsed time; Commits/turn divides by persisted assistant responses. Wait counts are backend observations, not percentages of elapsed time. Audit, polling and readers contribute to measured load. Client loop-lag, pool-use and append-to-read-lag samples are aggregated with SQL `unnest`/`percentile_cont`; there are no Python percentiles or per-run client timing files.

Formatted LOC: harness 600, smoke 75, DB-blip reproduction 37, initialization reproduction 63, this report 129. The generated per-point metrics JSON is not committed; rerun a point with `--output` to regenerate it. `psutil` is in the dev extra and the owner locked 7.2.2 in `ee4962c`; no SDK source changes.

All displayed quantiles below are native SQL results, rounded for display.

## Capacity

“Stable” here means the tested p99 stays within twice that worker count's unloaded p99 and correctness checks pass. It does not prove indefinitely sustainable capacity. Stable TPS is observed steady completions/s, not the configured offered rate; Poisson arrivals and boundary effects can put it above or below that rate.

The actual M8/rate16 lock snapshot contains 76 waiters across all eight workers and one holder, all on `(classid,objid,objsubid)=(1279872579,1213416264,1)`, key `0x4C494E4348534348`. This is Linch's shared schema-initialization lock in `storage/_pg.py`, not PgQueuer's install lock. The holder's last query begins `CREATE TABLE IF NOT EXISTS sessions`; it retains the transaction lock during ClientRead. Fresh store initialization revalidates metadata and executes schema DDL while holding this shared key. This establishes a serialized stage under load; one snapshot does not quantify its complete runtime share.

A separate M1/rate8 pool32 point has 601/601 completed, TPS 6.83, p99 17.919 s, worker CPU 96.1% and pool p99=32. Pool16 has 579/579 completed, TPS 7.03 and p99 16.961 s. This single comparison showed no benefit from the larger pool; it is not a replicated causal estimate.

## Chaos and reconnect

Full points use M4, rate 9.97, RTT 1 and one witness reader; lease TTL is 4 s and queue stall timeout 6 s. A terminal run may be failed: it is not the same as a completed run.

| Full case | Completed / terminal / durable | Ownership / stop outcome | Failure / retained work |
|---|---|---|---|
| Kill active owner | 766 / 767 / 767 | Epoch 1→2 at `2026-10-31 10:52:07.359856+07`, 6.418 s after signal, exceeding the 6 s target | One failed run; failed-without-error=1; no nonterminal runs |
| Disable DB proxy 3 s | 292 / 292 / 717 | No recovery; four worker processes exit | 425 nonterminal, each with a queue job; zero nonterminal-without-job orphans |
| Drain active worker | 744 / 744 / 744 | Zero post-signal claims by draining worker | All completed; all reported invariants zero |

SQL audit measures full-kill reclaim at 6.418198824 s, a recovery-time acceptance miss against the configured 6 s stall target. The full kill point has `terminal_count=1`, `failed_without_error=1` and `seq_gaps=1`. `terminal_count` checks both successful completion and exactly one result; it does not mean one run remained nonterminal. A controlled reproduction isolates the dangerous window: kill an owner whose run is running but `checkpoint IS NULL`. On takeover, starting the already-existing running run raises `ValueError: run ... already exists`; the worker records failed metadata without durable Error/Result events. Its `/tmp/wp18-init-repro.json` shows 169 completed plus one failed out of 170, the failed run still checkpoint-null, `meta.errors` containing that ValueError, and no error events. Its SQL-audited reclaim delay is 5.993983030 s. The targeted [initialization reproduction](../../../scripts/repro_worker_initialization.py) is 63 lines. This is a reproducible correctness failure at initialization, not a duplicate note or sequence-allocation race.

The full DB blip reports 36 API ConnectionRefusedError submissions, five lease-renewal failures and 30 reader retries. Its 425 unfinished runs retain jobs but automatic processing does not resume. Its `seq_gaps=369` includes unstarted/no-event runs because the check requires seq=1; it is not evidence of 369 holes in existing logs. The apparent p99 of 5.429 s covers only terminal members of the steady-arrival cohort and excludes the unfinished runs, so it is not a successful outage-latency result. Reader completion counters can predate the outage and do not prove reconnect completion after it.

The shorter quick run independently completes normal 34/34, kill 30/30 with SQL-audited 4.448634148 s reclaim and drain 30/30, but its blip completes 6/27, leaves 21 nonterminal and exits all four workers. A separate 37-line [two-worker reproduction](../../../scripts/repro_worker_db_blip.py) in commit `b02a12f` leaves 24/27 nonterminal with two exits. Stderr identifies the fatal PgQueuer LISTEN reset path ending in `InterfaceError: cannot call Connection.reset(): connection has been released back to the pool`. These observations establish a fleet-liveness failure with retained work, not lost jobs. No `src/linch` fix is included for either defect; resolve them and rerun the corresponding chaos gates before claiming crash or DB-interruption recovery.

## Validation and practical limits

The full code gates passed: 2,195 tests passed, 18 skipped; Ruff check and format check (419 files) passed; Pyright reported zero errors and zero warnings. The quick experiment exits 1 because of the confirmed DB-blip recovery defect. Final cleanup audit finds zero load schemas on both Postgres servers, zero experiment connections on the dedicated server, and zero remaining experiment worker/Toxiproxy processes. Passing unit/static gates does not override that failed resilience gate.

Capacity and network points above have no reported duplicate-note, writer-mismatch, missing-result or sequence invariant violations; all completed after drain. The full drain and fan-in cases pass; full kill and blip fail for the defects described above. The earlier shared-server exploratory measurements are not used as results for this dedicated-server matrix.

For this workload, four workers reach the same tested stable offered-rate bracket as eight. Use the measured stable throughput with headroom rather than equating configured offered rate with production capacity. Revalidate after addressing repeated store initialization, pre-checkpoint takeover and listener recovery. The single-host offline workload, short windows, one sample per point, asymmetric delay model and measurement instrumentation limit generalization.

## Reproduction commands

Use the main checkout venv Python and the dedicated TCP server. Commands below run bounded while holding the shared CPU lock; point schemas and subprocesses are removed even on invariant failure. The raw artifact records every exact point command, including the manual bracket refinements.

```bash
WP18_PYTHON=/home/duy/Downloads/duy_dev/agent_kit/.venv/bin/python
flock --timeout 900 /tmp/wp8-cpu.lock timeout -s INT -k 30s 50m "$WP18_PYTHON" scripts/load_test.py capacity --rate 2 --pool-size 16 --readers 1 --output /tmp/capacity.json
flock --timeout 900 /tmp/wp8-cpu.lock timeout -s INT -k 30s 12m "$WP18_PYTHON" scripts/load_test.py network --rate 9.97 --pool-size 16 --readers 100 --output /tmp/network.json
flock --timeout 900 /tmp/wp8-cpu.lock timeout -s INT -k 30s 10m "$WP18_PYTHON" scripts/load_test.py chaos --rate 9.97 --pool-size 16 --readers 1 --output /tmp/chaos.json
flock --timeout 900 /tmp/wp8-cpu.lock timeout -s INT -k 30s 4m "$WP18_PYTHON" scripts/load_test.py --quick --pool-size 16 --output /tmp/quick.json
"$WP18_PYTHON" scripts/repro_worker_db_blip.py
"$WP18_PYTHON" scripts/repro_worker_initialization.py
```

The network command compares zero and 100 readers at its middle point; the measured comparison above used one and 100. Reproduction scripts acquire their own bounded lock. The capacity command uses zero readers for the unloaded baseline and reports coarse geometric brackets; the recorded per-point commands reproduce the narrower brackets above. After measurement, fractional RTT input was rejected (previously it silently truncated); the capacity command now matches the measured zero-reader baseline. These guards leave the recorded integer-RTT point behavior unchanged. Persisted ErrorEvent types are grouped in the artifact; general `runs.meta.errors` aggregation is omitted, with failing initialization metadata captured by its reproduction. The earlier shared-server pilot passed 21/21 with no duplicates, gaps or owner mismatches; it is not included in the capacity estimates.
