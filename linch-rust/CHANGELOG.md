# Changelog

Notable changes to `linch-rust`: the Rust crates under `crates/` and the
`linch-rust` Python client that ships the `linch-server` binary. The Python
package `linch` has its own [changelog](../CHANGELOG.md).

## Unreleased

### Fixed

- Compaction triggered late when the harness's token estimate undercounted the provider's, which live runs measured 20% to 2x low (DeepSeek 3426 estimated against about 4342 reported, vLLM log-like text 2672 against 5485) before counting the system prompt and tools it leaves out. In a scripted run whose real prompt was twice the estimate plus 1500 tokens on an 8000-token window, the trigger never fired, the provider refused the prompt at turn 13 and the summary that refusal forced did not fit either: the run ended `failed`. The trigger now measures the view as the larger of the estimate and the prompt tokens the provider reported for the latest accepted call plus the estimate of what followed it (`compaction::Anchor`), rebuilt from the run's receipt and `compaction` events on a resume; the same run ends `success` with no prompt refused. A provider that reports less than the view weighs delays nothing, and the first turn and the turn after a compaction use the estimate. Micro-compaction is judged on the measure less what clearing removes. `tokens_before`, `tokens_after`, the `not_smaller` check and the hold's margin stay estimates; the `compaction` event gains `measured_tokens` (off the wire when the estimate was the measure; Python `CompactionEvent.measured_tokens`), which a resume reads back to judge whether an applied summary left the view still due.
- A prompt the provider refused as too long no longer ends the run `failed` when the summary that refusal forced did not fit either. A forced summary read the whole folded part, so one giant tool result in it, or a folded part that alone passed the window (a trigger at or above the window, say), was refused too; a giant result in the kept turn could not be summarized away at all. In a scripted run on an 8000-token window (real prompt 2x the estimate plus 1500) the three cases below ended `failed`, each ends `success` now: a 10000-character result in the folded part (before: `primary 6 ok 1 refused; summaries 0 ok 1 refused`; after: one refused summary, then the retry), a 20000-character result in the last turn (before: one summary and the run failed; after: two clips, no summary bought for it), and `threshold_tokens` equal to the window, where the folded part was many mid-size results (before: `primary 13 ok 1 refused; summaries 0 ok 2 refused`; after, over 60 turns: the turn-start summary of the whole view is refused, and it goes again on the folded part clipped, without spending `max_forced`). A trigger at or over the window still leaves a refused primary prompt to chance, and each one forces a summary that spends `max_forced`: raise it for such a trigger. A forced summary request now reads the folded part clipped to a budget (tool results first, head and tail kept around `[... N bytes omitted ...]`, UTF-8 safe, one cap across all texts) and, when the provider refuses that request as too long too, asks again on half as much, up to four requests, each paid and logged (a `compaction` event with `rejected` starting `context_length`), read back from the durable log on a resume. A last turn too big for the window is clipped in the view as a logged projection (strategy `clip`; the session's log keeps the full result), to half the window and then half again at each further refusal. The first request of a summary at a turn's start is byte for byte what it was (golden file pinned); one the provider refuses as too long goes again the way a forced one does. The one size case that still ends `failed` is a prompt whose system prompt, tools and last turn exceed the window once everything is clipped; it ends with a message that names the window and the estimated tokens of each part. The `compaction` event gains `clipped_bytes` (off the wire when nothing was clipped; Python `CompactionEvent.clipped_bytes`), and `Phase::Cleared` gains an optional `clip` budget. The crash test #172 left out (the hold read back from `measured_tokens` on a resume) is added.
- `RunLeased.owner` was `"linch-rpc"` for every server, so a refused resume could not tell which server drives the run. A server now claims runs under an opaque id (8 random hex characters printed at startup, or the new optional `server_id` of the config), the same for all its tenants and connections; it is the `owner` of the refusal and of the run row's lease. The worker's default owner is that id too, instead of `linch-server-<pid>-<start time>`, which a tenant could read in a refusal. `Tenant::with_server_id` and `new_server_id` are the library side; a `ServerConfig::build` result carries `server_id`.
- `liveness.keepalive_idle_ms` and `keepalive_interval_ms` were documented "at least 1" but the kernel takes whole seconds, so a sub-second value was accepted and then failed with `EINVAL` on every accepted connection (no keepalive on it, a warning per connection). The fields are now `keepalive_idle_secs` and `keepalive_interval_secs` (whole seconds, 1 to 32767; defaults 30 and 10), `keepalive_probes` is 1 to 127, and a value the kernel would refuse is refused when the config loads. The old `_ms` names are unknown fields and stop the server at startup: rename them (3.x, no alias). The TCP user timeout is capped at the largest value the kernel takes.
- A silent WebSocket was dropped at the first ping tick after `pong_timeout_ms` had passed, not at `pong_timeout_ms`: with the defaults a client whose last frame landed just after a tick was dropped after up to 90 s, not 60 s. The server now judges the silence as it grows (`pong_timeout_ms` after the last frame, whatever `ping_interval_ms` is), so the documented time is the real one.
- A job that gave up after 5 attempts read `failures: 4` in `job.list` next to "gave up after 5 failed attempts": the failing attempt is now counted, so it reads 5 (a `done` or `superseded` job still reads 0, as `job.list` documents).
- A background `Bash` command's status was unreachable once it failed: a command killed for flooding read `status: output_limit` in the docs, but its `tool_call_end` event had no `metadata`, because only a successful result's metadata reached the event. `Bash`, `BashOutput` and `BashKill` now carry `status` (`running`, `exited`, `timed_out`, `killed`, `output_limit`, `interrupted`), `exit_code` or `signal`, `truncated` and, for a background command, `process_id` in the end event's `metadata`, failed or not; a failed call's `ToolOutputError.details` object is the event's `metadata`. The text the model reads is unchanged, and a failed poll is still not marked `poll_done`.
- A tiny compaction trigger no longer buys a summary at every turn. With `threshold_tokens` 2500 and turns of about 600 estimated tokens, 10 of 12 turns compacted, each a paid summary call, because the view after a compaction (checkpoint and kept turns) was still over the trigger; the hold covered only rejected summaries. A summary that is applied and leaves the view still due now counts like a rejection: after 2 in a row the run asks again only once the view has grown by a tenth of the context window, and one that leaves the view under the trigger clears the count. The count is read back from the run's `compaction` events on a resume.
- An accepted compaction never reports `tokens_after == tokens_before` (2020 to 2020 once in 38 live compactions). The size check compared the checkpoint with the folded part, each estimated alone, while the event reports the whole view; with the estimate at four characters per token the two roundings could disagree. The check now rejects (`not_smaller`) any compaction whose whole view is not estimated smaller, by the same two numbers the event reports. The checkpoint builder keeps a whole token under the folded part, so the harness's own padding never makes the check discard a paid summary.
- The loop guard no longer ends a fix-and-test run whose test prints the same failure after each patch (`repeated_tool_call`, "same inputs and the same result 3 times"): a write or exec call that succeeds with a new input now clears the same-result count of every other call as well as the identical-input count. The same call with the same result and no patch between still ends the run at the third.
- A command started through `SubprocessHost` no longer outlives a client that dies by `SIGKILL` (the docstring said nothing outlives the server that asked for it, which held for server death, close and timeout, not for client death). Each command now has a watchdog, a `/bin/sh` of shell builtins in a session of its own that reads a pipe only the client holds and kills the command's process group when the pipe closes, as the server's `Bash` and MCP lifelines do; a command that ends on its own releases it first. Docs list what dies when.
- A rejected compaction summary is no longer asked again at every due turn: after 2 rejections in a row (a tool call, no text, or a checkpoint no smaller than the folded part) the run asks again only once the estimated view has grown by a tenth of the context window, or when the provider refuses the prompt (a forced summary is never held). An accepted summary clears the count; the count is read back from the run's `compaction` events on a resume. Every rejection still writes its `compaction` event, whose `rejected` text says when it asks again.
- The compaction saving check measures the whole checkpoint (header, summary, verbatim user messages, skill reminders, restated catalog changes), not the model's text alone: the verbatim section used to be added after the check, so a checkpoint could be larger than the part it replaced (1832 tokens for 1203). The verbatim blocks shrink to fit; a checkpoint that cannot be smaller is rejected as `not_smaller`.
- The loop guard no longer ends a healthy fix-and-test run: a write or exec call that succeeds with a new input (not among the latest 50 such calls) clears the identical-input count of every other call, so ten test runs between ten edits are no loop. The same call, a cycle of write or exec calls, or an edit and its undo, run again and again with no new edit between, and read-only cycles, still trip.
- A `before_provider_call` hook that leaves a `required` tool choice with no tool offered no longer sends the request that every provider answers with a 400: the turn goes out with no choice, and `context_build` `metadata.tool_choice_dropped` is `required`. A named choice dropped on a turn with no tool goes out with no choice, not `auto`.
- A completion gate's correction no longer names a tool the turn does not offer (a skill narrowed the tools), as a prerequisite's refusal already did.
- Loop guard docs: it counts one input at most 10 times in the latest 50 results, so a cycle of more than 5 distinct calls with ever-changing results is not caught; `max_turns` and the budget, both unset by default, are the only backstop for it and for an MCP `polls` tool whose answer changes every time.
- A cost cap needs a price. `budget.max_cost_usd` on a model with no price (neither the built-in table nor the agent's `pricing`) counted every call as free, so it never tripped and the run passed in silence. `agent.open` now fails (`-32011`, `BuildError::Invalid`) with a message that names the model and says to set `pricing` or use `max_tokens`; and a run whose call has usage and no price (the provider served another model, a fallback, one the pricing lacks) ends with a `BudgetAccountingError` before its next call. A token cap alone is unchanged.
- A cost cap needs a price for every model that can serve. `agent.open` with `budget.max_cost_usd` now also fails (`-32011`) when a `fallback_models` entry has no price, naming that model; it used to fail only for the primary, and an unpriced fallback was caught by the runtime guard once it served a call.
- A workflow's `max_cost_usd` is no longer a cap that never trips for an unpriced agent: `workflow.start` refuses it (`-32011`, naming the model, saying to set `pricing` or use `max_tokens`) and a call is refused with `WorkflowError::BudgetUnpriced` (`-32046`, `data.kind: unpriced`) when the agent has a model with no price. A finished call that had usage and no cost (a served model the pricing lacks) makes the workflow's next agent call fail the same way, on a resume too (the journal record carries the model, off the wire when priced). This also covers the tenant `workflow` ceiling `max_cost_usd`.
- A tenant's runs need a bound. Tenant admission (`agent.open`, and a worker opening a stored schedule or job definition) now refuses a spec with neither `max_turns` nor a `budget` with `max_tokens` or `max_cost_usd` (`-32004`, `kind: run_bound`, naming both settings; the `profile`'s and a `deep_agent` profile's `max_turns` count). A model that keeps calling a tool, such as an MCP `polls` tool on an agent with no bound, used to run on the operator's key until the loop guard, which an input that keeps changing evades. **Existing tenant configs without a bound are refused**, and a stored definition without one fails its job (each fire of its schedule too) with the reason shown in `job.list`; set `max_turns` or a budget and open the agent again. Nothing is injected into the spec, so run contract digests do not change. A trusted `local_namespaces` root and a stdio client keep their behaviour.
- `exec.start` carries the `principal` of the run that made the command (`{tenant, user, roles}`, off the wire when the run has none; `RemoteCommand.principal`, Python `ExecStart.principal`, the field defaults to `None`). Runs of several principals on one agent share the client's exec host, which the server does not scope; a host that serves more than one principal can now scope or deny each command by it. `SubprocessHost` ignores it. `exec.read` and `exec.kill` are unchanged: they name the command, which the host saw at `exec.start`.
- `spec.call_timeout_ms` under 100 (`0` included) fails `agent.open` (`-32011`, naming the field): `0` ended every tool call with a timeout at once.
- Docs: Anthropic's Sonnet 5.5 migration guide says its sampling parameters (`temperature`, `top_p`, `top_k`) return an error, and does not say a default value passes; the provider docs and the adapter comment say so with the date read. vLLM's `reasoning_effort` can be set by `request.extra_body.reasoning_effort` for a template that does not take `xhigh` (a test pins it). Only vLLM has live tests: the SGLang profile and the `GET /props` read of llama.cpp are checked against documentation only.
- Tests: the two `Bash` background tests that watched `/proc/<pid>` ask `ps` where there is no `/proc`, so they no longer pass without checking anything on macOS.
- `workflow.start` takes a `principal` (`run_workflow(..., principal=...)`): it is admitted as for `run.start`, becomes the principal of every agent call's run, so permission rules keyed on a role apply to a workflow's calls, and is stored with the journal (`linch_ext_workflows.principal`, migration 2 of linch-ext). Starting an existing id with another principal, or none, or one where it had none, is refused with `-32004`, `kind: workflow_principal` (`JournalStoreError::PrincipalMismatch`), and changes nothing. `JournalStore::claim` and `WorkflowOptions` take the principal. A workflow without one works as it did.
- The tool cache key carries the run's principal (tenant and user), so a principal-aware read tool such as `MemorySearch` with `scope: namespace` no longer serves one principal's cached result to another; a run with no principal keeps its key.
- `tool_cache.quota` is no longer part of the run contract: the operator's cap is set at every admission, and changing it made stored and scheduled tenant runs a `ContractMismatch`. The contract digest of a spec without a quota is unchanged.
- Credential-named request headers (a key header, or a name with `token`, `key`, `secret`, `auth` or `cookie`) are scrubbed from a provider's error text at any length; other headers still need 8 bytes. `Debug` of `Schedule` and `RunRequest` hides the agent definition, and a stored definition that does not decode fails its job with fixed text and the cause in the log.
- Docs: a provider header value is hidden from `Debug` in the Rust types only (a Python config is a plain dict); the sandbox's seccomp filter is a denylist, with Landlock and the non-root check as the boundary; `workflow.status` of an unknown id is `-32021`; the per-tenant rate window uses a monotonic clock.
- Docs and the `build-agent-with-linch-rust` skill match the code: the hook point count (23, 13 of them observe-only), the tool pipeline as hook points, config rows for `memory`, `pricing`, `tool_retry` and `tool_cache`, the `verification` and `steer_received` events, migrations `0007` and `0009`, memory, schedule and ledger tools in the architecture pages, the compaction summary request, stale line references in the turn lifecycle page, and decision guidance in the skill for steering, compaction, `tool_choice`, loop guard, policy, retry and cache, memory, execution backends, provider capabilities, schedules and tenant `allow` flags.
- Docs and the skill match the final stack: one row per error code in the `rpc.md` table (every constant of `error.rs`, with its Python class) and the families in `troubleshooting.md` (provider questions, schedules, workflows, steers, cost caps and `run_bound`), a workflow error table, `remote_execution` as a reason for `-32040`, the tool cache key with the principal, line references moved to the code after the loop, compaction and steering changes, and the skill's rows for cost caps and `pricing`, `call_timeout_ms`, tenant run bounds, steering limits, compaction rejection, workflows with a principal, remote execution, `liveness` and `LINCH_LOG`.
- Provider questions (`provider.capabilities`, `provider.models`, `provider.model`) and `agent.open`: a tenant's `base_url` can no longer steer the server's key to another path of an allowed origin. `provider_base_urls` entries now match the path as well as the origin: an entry with a path allows that path alone, one without allows each provider's own (`/v1` for OpenAI, none for DeepSeek, Anthropic and Gemini, `/v1` or none for vLLM, SGLang and llama.cpp), where the path used to be ignored (list a gateway's prefix in full). Every adapter refuses, when built, a base with a query, a fragment, userinfo, an escape, a backslash, or a `.`, `..` or empty path segment (`ProviderError::InvalidRequest`); `https://host/v1/files#` made a models call a `GET /v1/files`.
- `provider.capabilities` is keyless: `build_keyless` never reads the provider's key from the environment, so a self-hosted server's window probe carries no `Authorization` header. Every window probe (also at `agent.open`) reads at most 64 KiB of the answer.
- `provider.models` and `provider.model` errors no longer tell a closed port from a slow host or carry the vendor's words: `ProviderRequestFailed.kind` is `unreachable` (connect, reset, timeout), `status`, `invalid_request` or `other` (`connect` and `transport` are gone), with one fixed message per kind. A vendor error text, where an adapter keeps it, is ASCII printable and at most 120 characters, from the first 8 KiB of the answer; a listed `display_name` loses control and direction characters and is cut at 100.
- `provider.models` and `provider.model` are limited to 10 calls a minute per tenant (`-32005`, `kind` `provider_calls`); a local connection is not limited.
- A model list cut at the page cap says so: `Provider::list_models` returns a `ModelList` (`models`, `truncated`; `truncated` is off the wire when false), `provider.models` and `Server.list_models` (a `ModelList`, still a `list`) carry it, and a `ModelNotFound` on a cut list has `truncated`.
- `schedule_fire` events are written with `ignorable: true`, so a build that predates the kind skips it instead of failing with "unknown event type" on a scheduled run's events.
- `ProviderCapabilities.native_output_schema` is now `output_schema: "native" | "final_tool"`: `final_tool` does not say the server cannot do structured output. vLLM takes a `response_format`, but with tools in the same request it binds the whole answer to the schema and never calls a tool (checked live), so a run there offers its final tool; SGLang and llama.cpp keep the same rule, unchecked. The `Provider::native_output_schema` method and the `scripted` provider's field are unchanged.
- Event docs: durable seqs have gaps by design (the dispatch and receipt records take seqs no client receives), so a gap alone does not show a lost event; a resume emits a second `init` with `resumed=True`; and an interrupted tool call is closed with an error `tool_call_end` on resume, which the resume test now checks (its comment said the opposite).
- DeepSeek prices: `total_cost_usd` stays `None` for DeepSeek without `pricing`, on purpose. The official page prices each model at two rates by the hour (off-peak is half of peak), so one built-in row would be wrong half the time; the monitoring docs give the 2026-11-17 peak rates, cache hit and miss, to set per agent, and a test prices a cache hit apart from a miss.
- `spec.temperature`: the agent spec had no temperature, so 0 was impossible. It is 0 to 2 (`anthropic` at most 1, `Provider::max_temperature`), goes with every request when set and stays off the wire and the contract when unset; `agent.open` fails for a value out of range. The docs say which providers ignore or refuse it.
- `init.tools` lists the final tool a run made from its output schema, after the agent's tools, on a first and a resumed `init`; it was empty of it while `init.final_tool` named it, though the model was offered it.
- MCP stdio servers no longer outlive a `SIGKILLed` `linch-server`: a small watchdog per server kills the server's process group when the client's end of its pipe closes, as the `Bash` tool's lifeline does for background commands. A server that ignores stdin EOF and `SIGTERM` was left running.
- vLLM `reasoning_effort`: the Qwen3 chat template takes only `low`, `medium` and `xhigh`, so `spec.effort` `high` and `max` are sent as `xhigh` instead of ending the run with an HTTP 400. SGLang and llama.cpp send the level as it is.
- Pruning keeps what a continuation needs: `prune_history` keeps a history row or failed job that names a stored agent definition while its run is not terminal, and `prune_definitions` keeps a failed job's definition for the same time, so `enqueue_approve` and `enqueue_resume` of a scheduled run that waited past `history_retention_ms` still find their agent. Before, they queued a job with no agent that no worker with only a factory takes, which blocked the run (`RunBusy`) and its tenant's job cap for good. A continuation whose named definition is gone is refused (`WorkerError::Invalid`). The rows go with the first prune after the run ends; no migration.
- `linch-server` writes the `tracing` records of the worker, the scheduler and the workflow journal to stderr (warnings and errors by default; `LINCH_LOG`, or `RUST_LOG`, sets the filter): without a subscriber every `tracing::warn!` went nowhere. Adds `tracing-subscriber` (`env-filter`, `fmt`), which removes the need for a hand-written sink and makes the documented "goes to the server's log" true. stdout still carries only the protocol.
- A run holds at most 16 steers waiting for its next step: a steer past that is refused at once with `SteerQueueFull` (`-32005`, `kind` `steers`, the limit the unread steers already had), so waiting steers no longer hold the connection's 64 request places and a `run.cancel` on the same connection is always read.
- A client that vanishes without closing its HTTP connection no longer keeps its place for good: the server sets TCP keepalive and a TCP user timeout on accepted sockets (30 s idle, 3 probes 10 s apart), pings each WebSocket every 30 s and ends one silent for 60 s, which frees its `max_connections` place, its workflow hold and its calls. The `liveness` section of the server config sets the times. The Postgres connection that holds a workflow sets `tcp_keepalives_*` too, so a vanished server host frees the hold in about a minute. Adds `socket2` (already in the lockfile through tokio) for the socket options tokio does not expose.
- A workflow answer applies only to the question that was asked: the stored interrupt's key and an equal payload (canonical digest). A draft edited between the question and the resume asks again, drops the answer with an `interrupt_stale` event and journals nothing; before, the earlier approval was applied to it. An answer for a workflow that was not parked, or for an interrupt other than the stored one, asks again too.
- `workflow.start` with `resume` answers for a workflow whose journal holds nothing (a memory-store agent on a new connection) is refused with `-32049` (`WorkflowNoJournal`) before anything is claimed, instead of running everything again, steps included.
- The tool cache tries a failed clear once more before it stops caching for the agent, and logs one `tracing` warning when it stops. Docs say what a failed clear leaves: other agents and servers on a shared Postgres cache serve the entries until their ttl.
- Docs: what the scheduler's pruning removes and what it does not (runs and sessions of schedules stay, about 1,440 a day at a 60 s interval, and no call removes them); a steer that fails after its claim can leave a suspended run showing `running` while approve, answer, cancel and resume still work; how recall time grows with a scope's memories (about 80 ms at 60,000, 630 ms at 600,000, timing out above about 200,000) and how to size `max_memories_per_scope`; a memory-store agent's workflow runs everything again after a new connection; `run.steer`'s invalid-steer code is `-32038`.
- Docs: a `run.cancel` with steers waiting keeps them (journaled, delivered as `alignment` events of the aborted run, seen by the session's next run); `ContextBuildEvent.budget.dropped` is ordered by callback and index, not by drop order; `effort` is a request (measured on vLLM with a Qwen3 model: every level ran, reasoning tokens not rising above `medium`); a memory-store agent's server memory grows about 110 KB per run for the life of the agent (use Postgres stores for long-lived agents); the Python client cannot send NaN, so the server's temperature check is the only one for a client that can.

### Added

- `spec.tool_result_cap`, `{"max_tokens", "head_fraction"?}` (`ToolResultCap`; Python `ToolResultCap`): one bound, in estimated tokens (four bytes per token, at least 128), on what a tool result puts in the model's view, for host tools and any tool without a cap of its own. A larger result shows its head (30% by default), a marker `[... N bytes omitted; read them with ReadToolResult(tool_use_id="...", offset=H) ...]` and its tail; the whole result stays in the `tool_call_end` event, the checkpoint and the session's audit history (the results message is appended as two entries in one write, the whole one for `full_history` only and the cut one for `provider_view` only), so a resume cuts the same bytes, the loop guard and `tool_cache` see whole results, and compaction measures the cut view. The agent gets a `ReadToolResult` tool (`tool_use_id`, `offset`, `limit` in bytes, read scope) that returns any slice of the whole result with the next offset, never over the cap. Off by default and off the wire, so the contract digest of a spec without it is unchanged. In a scripted run of 30 turns with results of 2, 12, 60 and 200 KB the last request weighed about 485000 estimated tokens without the cap, 142000 with 8000 and 86000 with 4000.
- Directed workflows over RPC: `run_workflow(agent, fn, run_id=...)` runs a Python function in the client whose `wf.agent`, `wf.step` and `wf.interrupt` calls the server journals in Postgres (`PgJournalStore`, memory for a connection's life), so a crash of the client or of the server resumes the same `run_id` without repeating a finished call, and an edited prompt re-runs only its own call. `WorkflowContext` also has `parallel`, `settled`, `pipeline`, `phase` and a shared `Budget`; `wf.agent` takes `subagent`, `output_schema`, `key`, `fork` (a session an earlier call returned), `timeout_ms` and `retry`. Wire: `workflow.start`, `workflow.agent`, `workflow.step.begin`, `workflow.step.complete`, `workflow.interrupt`, `workflow.cancel`, `workflow.finish`, `workflow.status` and the `workflow.event` notification; codes `-32045` (held by another client) to `-32048`. A workflow has one driver at a time (a Postgres advisory lock plus the lease epoch). A tenant needs `allow.workflow` (off by default) with caps on concurrent workflows, journal records, record size, agent calls in flight and a budget ceiling. Docs: [Workflows](docs/usage/workflows.md).
- `run_or_resume(agent, run_id, prompt)`: starts a run under a chosen id, returns the result of a finished one without a model call, continues an unfinished one (waiting out another process's lease), and returns the `SuspendedEvent` of one that waits; for job queues and orchestrator nodes. `run.start` of a stored id is now the `RunExists` exception (`-32023`).
- `WorkflowSession::open_held`, `step_begin`/`step_complete`, `WorkflowContext::scoped`, `agent_with` (`AgentCall`, `AgentOutcome`), `WorkflowBudget`, `LiveGate`, `JournalStore::hold` and `WorkflowOptions::{budget, max_records, max_record_bytes, live_gate}` in `linch-ext`: what a host that drives the calls itself needs. A workflow agent call's journal value is now an object (`text`, `structured`, `session_id`, `tokens`, `cost_usd`); a journal written before it is not read, so start a fresh workflow id.
- Provider request settings: `request.extra_body`, `request.default_headers` and
  `request.timeout_ms` on every live provider, and `chat.parallel_tool_calls`,
  `chat.include_stream_options`, `chat.chat_template_kwargs` and
  `chat.sampling_params` on the Chat Completions providers (`deepseek`,
  `openai-chat`, `vllm`, `sglang`, `llamacpp`). A caller's key header
  (`authorization`, `x-api-key`, `x-goog-api-key`, `api-key`) replaces the
  provider key for every call (a turn, a model list, a window probe), which
  then need not be set. Header values are hidden when a config is printed and
  removed from error text. `extra_body` cannot replace the model, `stream`,
  `temperature`, the conversation, the tools, `tool_choice` or the vendor-side
  state fields (`store`, `previous_response_id`, `conversation`); Gemini's
  `generationConfig` is merged with the request's fields winning. A remote
  tenant may set `request` and `chat` only with the allowlist
  `provider_request` (`allow.provider_request` in the server config), never a
  key, `cookie`, `proxy-*`, `forwarded` or `x-forwarded-*` header, and within
  16 headers of 1 KiB, 16 KiB of body fields and a 600000 ms timeout.
- Steering: `Agent.steer(run_id, text, steer_id=None)`, `Run.steer(text)` and `run.steer {agent, run_id, text, id?, principal?}` (answer `{queued, id}`) send text to a run that is going on, the Rust counterpart of Python's `session.align`. The steer is a journal-only `steer_received` event written by the run that holds the lease and flushed before the caller is answered; the run logs it as a user message of its own (a `user` event with `subtype` `alignment` and `steer_id`) after the tool results of the current batch and before the next model call, or, when the model answered without tools, before the run would end, which then takes another turn. A suspended run takes it too and reads it once it continues; a finished run is `RunTerminal`, a run another server drives `RunLeased`. An idle run (queued, or running with no server driving it) is `InvalidSteer`: resume it first. A resumed run rebuilds what is pending from its journal, so a steer is logged once at any crash point (tested at every write). At most 16 KiB and 16 unread steers a run (`InvalidSteer` -32038, `LimitReached` `steers`); the text passes prompt redaction and the `user_prompt_submit` callbacks (request `source` `steer`). With memory stores nothing survives the process. Unlike Python: the call answers once the steer is durable, no images, and no routing to another server.
- Task ledger: `AgentConfig.task_ledger` (`{list, max_chars?}`, needs `tasks`) makes every session of the agent share one task list and shows its open tasks with each request through a `context_build` hook (policy id `linch.tasks.ledger-context`, never logged, bounded, pin it in `context_budget`). Off by default and off the wire when unset; a tenant needs `allow.task_ledger` (default false). [Long-running agents](docs/usage/long-running.md) documents the goal contract (a system section), the ledger, artifacts, steering and an independent done check as the pattern for agents that run for hours.
- System prompt sections and a context budget: `spec.system` (`sections` with a name, text, `order` and `cacheable`, `append`, `replace_defaults`), Python's `SystemPromptConfig`, and `spec.context_budget` (`max_tokens`, `drop_order`, `pinned`), Python's `ContextBudget`. Sections are sent first, sorted by `order`, as system blocks with their cache flags (a non-cacheable section may not precede a cacheable block, or the agent does not open); `append` goes after the prompt and the skill listing; `replace_defaults` leaves out the text the deep agent, filesystem and profile presets add to the prompt. The budget caps what `context_build` callbacks and hooks add to a request (retrieved memory, file memory) at four characters per token, drops whole blocks by the declared order (callbacks named in neither list first, then `drop_order`, never `pinned`), never fails the run, and reports `dropped` and `over_by` on the `context_build` event's `budget`; the decision is recomputed per request, not logged for recovery. Both are in the contract only when set, so existing contracts do not change. A tenant is bounded to 16 sections, 16 KiB each and 64 KiB in all, and `allow.system_sections` adds operator sections to every tenant agent that cannot be removed. `System`, `SystemSection`, `ContextBudget` and `ContextBuildEvent.dropped` in the Python client. Python's grounding check (`register_grounding_check`) is not built.
- The tool pipeline. `post_tool_use` callbacks may answer `mutate` (a new `content` value, or `is_error`, keeping the result's metadata and error code); the next request and the session log carry the mutated result. A new `tool_execute` hook point is the waterfall around the tool body, Python's `tools/execute`: `Hooks::tool_execute` (a `ToolPipeline`) takes `ToolMiddleware` layers that await `Next::run` or veto a call by not doing so, once per attempt, first registered outermost; over RPC it is `hook.call` twice (`phase` `before`, then `after` when the layer asked for the result), and Python's `tool_middleware` decorator hides the two calls behind `async def layer(call, next)`. With no layer the tool is called directly and contracts do not change.
- Tool retry: `spec.tool_retry` (`max_attempts`, `base_delay_ms`, `max_delay_ms`, `retry_on`, `tools`) runs a tool again after an error result whose `code` is listed (or a `timeout`), with a doubling wait, only for a tool that declares itself `Tool::idempotent` (`Read`, `Grep`, `Glob`, and a host tool declared `idempotent: true`, Python's `@tool(idempotent=True)`; host tools report a class with `ToolError(code=...)`). Each retry is a durable `tool_retry` event before the wait, so a crash after it leaves a call a resume reports interrupted and never re-runs: a non-idempotent tool is never run twice. Tenants may not ask for more than 5 attempts or a 60 s wait.
- Tool cache: `spec.tool_cache` (`tools`, `ttl_ms`, `max_entries`, `max_value_bytes`, `invalidate_on_write`) serves an identical call of a named read tool from a cache keyed by the agent's namespace, the session, the tool and the canonical input. A hit goes after permission and `pre_tool_use` and runs `post_tool_use`, redaction and the output schema as a fresh result does; its `tool_call_end` has `cache_hit`. Entries live in the agent, or in `linch_tool_cache` (migration 0008, `PgToolCache`) with Postgres stores; a write or exec tool clears the namespace before and after it runs; a store failure is a miss. A tenant needs `allow.tool_cache` and stays within 1024 entries, a one-hour ttl and 1 MiB a result.
- Tool pipeline review fixes. The tool cache key now includes the session (`scope: "session"`, the default and off the wire; `"namespace"` shares entries and a tenant needs `allow.tool_cache_shared`), a namespace has an epoch that a clear raises and a `put` made before it is refused (in memory and in Postgres, by an advisory lock per namespace), and the first background launch (`Bash` `run_in_background`, a background subagent; `Tool::launches_background`) ends caching for the agent. The cache stores only the tool's own result, and only when `tool_execute` layers returned it unchanged; a hit does not run the layers. Store calls are cut off after 2 s and by an abort (the clear after a write only by the 2 s), and an error or a timeout is a miss. A tool that keeps session state, `Read`, is `Tool::cache_safe() == false`, and naming it in `tool_cache.tools` is refused at build. A tenant's `tool_cache` needs `spec.redaction` over tool results, has its `quota` set to the tenant and `allow.max_tool_cache_bytes` (64 MiB) for all its namespaces together, and `allow.tool_cache`, `allow.tool_cache_shared` and `allow.max_tool_cache_bytes` are settable in the server config. A Postgres put sweeps up to 100 expired rows of any namespace. The `tool_retry` event's `error` is redacted and cut to 512 bytes, a run's retries, all its calls together, stop after 5 minutes, and a `post_tool_use` `mutate` with `content: null` is refused. Python's `tool_middleware` keys its parked calls by run, call, attempt and token, so one layer shared by two agents no longer collides. The tool cache migration 0008 changed before release (new columns, `linch_tool_cache_epoch`).
- Reliability policy: `spec.policy` states tool order and completion requirements. A prerequisite (`{"tool", "requires"}`) answers a call with an error result naming what to run first, without running it, its `pre_tool_use` callbacks or permission, until the required tools succeeded in an earlier batch of the run; it is an ordering aid, not a security boundary. A completion gate (`{"name", "succeeded"?, "min_calls"?, "check"?, "feedback"?}`: tools that must have succeeded, and a verifier check on the answer) holds the final answer, text or final tool, back with one correction turn per failure, up to `max_corrections` (2) in the run; the next failure ends the run `failed` with a `PolicyGateError`. Every decision is a `policy` event (`refuse`, `correct`, `stop`). Nothing is checkpointed: successes, refusals and corrections are read back from the run's log on a resume, with a crash test at every write. A subagent takes the prerequisites, not the gates. A correction is neither an idle nor a repeated turn for the loop guard. Unset is off, off the wire and out of the contract digest. A tenant's policy is bounded (32 rules, 1024-byte texts, 16 corrections) and added to the tenant's `required_policy`, never replacing it. `Policy`, `PolicyGate`, `PolicyPrerequisite` and `PolicyEvent` in the Python client.
- Reliability policy review fixes: a `tool_choice` that holds every turn and defeats the policy (`none` or a named tool with rules that need calls, `required` or a named tool with any rule and no final tool) is refused at `agent.open` and, for a run's own, with `InvalidToolChoice`; `required` with a final tool stays allowed. `max_corrections` is optional on the wire (`None` is 2 for a run and no cap when a tenant's policy is merged into `required_policy`), so a tenant that omits it keeps the operator's cap; an explicit `2` is now on the wire. A check gate's default feedback no longer shows the pattern or keywords, only an explicit `feedback` does. A final tool's input is checked as its JSON text and as the strings it holds, so a `forbids` pattern naming a quote or a newline is not dodged by JSON escaping, and a `stop` rewrite of the answer is checked again (a failure ends the run, no correction). A refusal names only tools the run offers this turn, and a tenant's open error does not name the tool of an operator rule it lacks. A refusal event is deduplicated by response and `tool_use_id`. The server config refuses a `required_policy` whose check does not compile (`AccessError::RequiredPolicy`, `ReliabilityPolicy::compile_problem`), a tenant's own is refused at `agent.open` with kind `policy`, and an open error caused by the operator's rules does not echo them. `required_policy` and the docs say what it enforces: the model's call order, not the tenant's host.
- Provider capabilities and model lists: `Provider::capabilities(model)` states, per adapter and as plain data, the context window (and whether the server, the adapter's table, the host or a default gave it), native output schema, tool choice (with the thinking states that refuse a forced one), thinking controls, vision, tool-argument streaming, prompt cache and stop sequences; the capability tests check each declared rule against the adapter's refusal and request body. `Provider::list_models` and `model_info` ask the vendor (OpenAI and Responses, DeepSeek with window, output limit and modalities, vLLM and SGLang with `max_model_len`, llama.cpp with `n_ctx`, Anthropic and Gemini paged), without the key or URL in any error. RPC `provider.capabilities`, `provider.models` and `provider.model` take a provider config, so a client asks before it opens an agent (`Server.provider_capabilities`, `list_models`, `model_info`; `ModelsUnsupported` -32035, `ModelNotFound` -32036, `ProviderRequestFailed` -32037). A tenant needs `allow.provider_info` (off by default) and an allowed `base_url`.
- Monitoring: a run a worker starts for a schedule fire has a durable `schedule_fire` event (`schedule_id`, `fire_at_ms`) right after `init`, in the same write; its OpenTelemetry spans carry `linch.schedule.id`. The Python client decodes it, and has classes for the three journal-only `model_call_*` kinds (the server never streams them). Runs without a schedule are unchanged.
- `tool_choice` and the final tool: `spec.tool_choice` and `Agent.run(tool_choice=...)` (`run.start`, stored in `init`) set whether and which tool the model must call, `auto`, `none`, `required` or a named tool; a named tool the agent does not offer, `required` with no tool, or a choice the provider refuses (DeepSeek a forced one while thinking, Anthropic with budgeted thinking, llama.cpp a named one), is refused at `agent.open`, and a run's own with `InvalidToolChoice` (-32034) before anything is written. Structured output now works on DeepSeek, vLLM, SGLang and llama.cpp: the run sends them no schema and offers a final tool made from it, forced when it is the only tool; its call ends the run with the checked input as `structured_output`, a bad input goes back as the call's error under `structured_output_retries`, and every way out leaves the session paired, a crash included (a `Finishing` checkpoint). `spec.final_tool_name` names a registered tool as the final tool, Python's `final_tool_name`. Agents that set none of this keep their contracts.
- Remote execution: `execution: {"backend": "remote"}` runs `Bash` (foreground, background, `BashOutput`, `BashKill`, timeout and cancel) in the client that opened the agent, through the server requests `exec.start`, `exec.read` (a long poll) and `exec.kill`. A timeout or cancel is reported only once the host confirmed the kill; a host that stops answering makes the call `interrupted`, never a made-up result. The agent cannot be scheduled, queued or run by a worker (`not_background`, reason `remote_execution`), has no file tools unless the policy's `shared_workspace` says the host sees the workspace, needs the entry in a tenant's `allow.execution` (denied by default) and never gets the server's `PATH`, `HOME`, `USER`, `SHELL` or `TMPDIR`. Rust: `AgentConfig::open_with_remote`, `RemoteExec`. Python: `Server.open_agent(execution=...)`, `ExecutionHost`, `SubprocessHost`, `RemoteExecution`.
- Schedule tools: `schedule_tools: true` gives the model `CreateSchedule` (exec), `ListSchedules` (read) and `CancelSchedule` (write), Python's `register_schedule_tools`. A model-made schedule runs the same stored agent in the calling run's session for its principal, under the tenant's `max_schedules` and `min_schedule_interval_ms` (the `schedule.create` admission); the model lists and cancels only its own agent's schedules in the calling session, as Python's tools do, and a subagent cannot create one. Off by default; `agent.open` refuses it without `max_schedules`, on a local connection, or for an agent that cannot run in the background.
- File memory for a plain agent: `filesystem.memory` (default false, off the wire) registers the deep agent's `FileMemoryContext` hook without the preset, so the model is told memories live under `/memories/` and sees the first 200 lines of `/memories/MEMORY.md`, Python's `FileMemoryContextBuilder`. Unlike Python, which reads the index once per run, it is read for each request: the blocks are request-tail only and never in the cached prefix, so a per-run cache would save one read and hide the model's own edits for the rest of the run. On the contract only when on. With Postgres stores sessions share the file; with memory stores `close_session` drops it. `memory` in the Python `Filesystem` TypedDict.
- Provider concurrency: `max_provider_concurrency` in the agent config, Python's `Agent(max_provider_concurrency=N)`, caps the provider calls in flight; a call over the cap waits first in, first out. It is a `ProviderGate` (`AgentBuilder::provider_gate`), shared by an agent's runs and its subagents', and by every agent opened with one `PgPools` on one provider key variable and endpoint, so a server's tenant stays under its cap however many agents it opens. A run that waits has staged no delivery: cancelling it leaves no call and no receipt, and a run that must wait writes what it had staged first. The place is dropped before a retry's backoff or a forced compaction's summary. Unset is no limit, off the wire and out of the contract digest. `allow.max_provider_concurrency` caps a tenant (above it: `provider_concurrency`; asking for none gets the cap); `max_provider_concurrency` in the Python `AgentConfig`. The limit is one process's: a Postgres-backed one shared with workers and other servers is not built, and neither is Python's pluggable `Limiter`.
- Loop guard: `spec.loop_guard`, Python's `LoopGuard`, on by default. The third call of one tool with the same input and the same result (not an error; Python counts identical inputs whatever the result), or the third tool batch in a row whose every call failed, ends the run `failed` with a `loop_guard` event (`repeated_tool_call`, `repeated_failures`) and a `LoopGuardError`; 0 turns a check off. One more check is always on: more than `max_idle_turns` (25) turns in a row without a provider call (a `before_provider_call` `force_continue`) ends the run (`idle_turns`), so that loop is bounded with `max_turns` unset. The counts are read back from the run's log on a resume. The default is left off the wire, so existing contracts do not change; a tenant may not raise `max_idle_turns` above 25. A tool whose `Tool::polls` is true is waited on instead (see the Fixed entry below). `LoopGuard` TypedDict in the Python client.
- Long-term memory: `memory: {scope?, recall?, max_memories?, max_memories_per_scope?}` gives the model `MemorySave` (write), `MemorySearch` (read) and `MemoryDelete` (write) over a `MemoryStore` the open binds from the stores: `PgMemoryStore` (table `linch_memories`, migration `0009_memories`; each memory keeps its words, in Unicode NFC, prefixed with a hash of its namespace and scope in a `text[]` GIN index, so a common word in one namespace never reads another's postings; no extension) or an in-memory store. It needs no callback, so scheduled and background agents have it. Every call is bound to the namespace and a scope; the scope is `principal` unless the config says `agent` (the shared scope lets one user's saved text, or an injected save, reach every user), and `principal` fails closed without a principal. The model never names either, and a store failure reaches it only as a fixed text. Queries are reduced to words before search, so no query can fail it or carry SQL, and every memory statement runs under a `statement_timeout` (2 s). What a memory says is untrusted: tag-like `<` and `[memory:` are escaped in search results and in recall. `recall: {k}` adds the top matches for the latest user message at the request tail, unlogged, inside `<memory-data untrusted="true">`, at most 8 KB, from a hook with a 300 ms timeout that fails open; it searches with the words that select (a small English stop list, English words under 3 letters and a few Vietnamese particles are left out, short words with diacritics stay) and needs two of them when the message has two or more. A save is keyed by run, tool call id and text, so a reused call id saves a different fact while a crash replay stays one row. A tenant needs `allow.memory: true` (denied by default) and `allow.max_memories`: the server refuses to load a config with memory and no cap, and admission refuses an agent for such a tenant. A scope may keep at most `max_memories_per_scope` (a quarter of the cap, at least 1, when unset) so one principal cannot fill the tenant's budget; caps are counted per tenant under an advisory lock and stop reading at the cap. `MemoryStore::search` takes a `min_match` and the trait has `purge(scope)`. Off by default and off the wire, so existing contracts do not change. `ContextBuildRequest` now carries the run's `principal`. `LongTermMemory` TypedDict in the Python client.
- `ProviderRequest.context_tail`: how many trailing blocks of the last message are request-only context (recalled memory, retrieval, any `context_build` block). The Anthropic adapter puts its conversation cache breakpoint on the last logged block before them, so the cached message is the same bytes on the next turn; before, the breakpoint sat on the unlogged context and every conversation cache entry was lost on the following turn. The other adapters ignore it (automatic prefix caching). Absent from the wire when 0.

- Cancel a suspended run: `Agent::cancel`, `run.cancel` with an `agent` handle, and `Agent.cancel(run_id)` / `Run.cancel()` in Python end a run waiting for an approval or an answer, from any process and across restarts on Postgres; each pending call gets a `Tool call aborted` result so the session stays paired, the run ends `aborted`, and a late approve or answer gets `RunTerminal`.

  writes to the workspace, a private per-session `HOME`/`TMPDIR` and system
  directories, and scopes signals; a seccomp filter refuses Unix sockets,
  `io_uring` and, with the network off, every socket; `prlimit` caps each

- Twelve observe-only hook points, for parity with Python's lifecycle hooks:
  `agent_start`, `agent_stop`, `turn_start`, `provider_call_start`,
  `provider_call_stop`, `tool_use_start`, `tool_use_stop`,
  `post_tool_use_failure`, `pre_compact`, `post_compact`, `subagent_start`,
  `subagent_stop`. Each answers `()` (`{}` on the wire), can never fail
  closed, and costs nothing when no hook is registered on it. Available to
  `@callback` in `linch_rust` and to `Hook<P>` implementations in
  `linch-core`.
- `before_provider_call`: a hook point for the full provider request about to
  be sent. A hook may rewrite it (the rewrite is what is sent and what
  `context_build` records) or block the call, ending the run before the
  provider is ever reached. Defaults open, but unlike the observe-only
  points its blocking answer can fail closed. Available to `@callback` in
  `linch_rust` and to `Hook<BeforeProviderCall>` in `linch-core`.
- `after_provider_call`: a hook point for the response a provider call just
  assembled, before it is staged and appended to the session. A hook may
  rewrite it (the rewrite is what gets staged and appended) or block it,
  ending the run before anything is staged. Defaults open, but like
  `before_provider_call` its blocking answer can fail closed. Available to
  `@callback` in `linch_rust` and to `Hook<AfterProviderCall>` in
  `linch-core`.
- `stop` can now rewrite the run's final-answer text, or block the stop
  outright. This is Python's `before_final_answer` hook point, folded into
  `stop` rather than added as a separate point: the rewrite replaces only the
  text the run reports as its result, not the assistant message already
  appended to the session (that message is logged before `stop` ever runs).
  Available as `{"action": "rewrite", "text"}` / `{"action": "block",
  "reason"}` to `@callback` in `linch_rust` and as `StopResponse::Rewrite`/
  `StopResponse::Block` to `Hook<Stop>` in `linch-core`.
- `event_emit`: a thirteenth observe-only hook point, for parity with
  Python's `EVENT_EMIT`. It fires once per event, in delivery order, but
  only for an event that is both streamed to the caller and durably logged:
  never for a hook's own record (it would otherwise recurse into itself)
  and never for a stream-only delta or tool-progress event. Answers `()`
  (`{}` on the wire) and can never fail closed. Available to `@callback` in
  `linch_rust` and to `Hook<EventEmit>` in `linch-core`.
- `after_provider_call` can retry, as Python's `retry`/`force_continue` there: the response is kept and logged, none of its tool calls run, and the feedback goes to the model (in a `<system-reminder>`, or as the first call's error result) before another turn; `{"action": "retry"|"force_continue", "feedback"}` on the wire, `AfterProviderCallResponse::Retry` in `linch-core`.
- `stop` can retry the final answer once per run call, as Python's `before_final_answer` `retry` (`_MAX_FINAL_ANSWER_REENTRIES`); a spent retry counts as `allow`. `{"action": "retry", "feedback"}` on the wire, `StopResponse::Retry` in `linch-core`.
- `stop` accepts `{"action": "force_continue", "feedback"}`, Python's name for its `continue`.
- `before_provider_call` accepts `force_continue`, as Python's there: the call is skipped, the feedback goes to the model in a `<system-reminder>`, durable before the next turn, and the run takes another turn, bounded only by `max_turns`; `{"action": "force_continue", "feedback"}` on the wire, `BeforeProviderCallResponse::ForceContinue` in `linch-core`. `retry` stays refused there.
- `Phase::AssistantReceived` records an `after_provider_call` retry in an optional `retry_feedback`, durable with the paid response; checkpoints without one are unchanged, but a binary older than this one cannot resume a run whose checkpoint has one.
- `spec.provider_retry` retries a provider call that failed with a retryable error (no connection or no response, 408, 429, 5xx) on the same model, after an exponential, jittered wait that honours `Retry-After`: `{"max_attempts"?, "base_delay_ms"?, "max_delay_ms"?, "jitter"?}`, on by default with Python's `RetryOptions` (5, 1000, 30000, 0.2); `{"max_attempts": 1}` turns it off. The default stays off the wire, so a spec that does not set it keeps its run contract. Each attempt is its own durable delivery; a crash during the wait resumes with the next attempt and keeps the turn's count. `ProviderRetry` in `linch-core` and the Python client.
- A run that retried or failed over holds `provider_retry` / `model_fallback` events, which a binary older than this one refuses as an unknown event type: it cannot read or resume such a run (the error is explicit; nothing is resumed wrongly). Since retries are on by default, any run that met a retryable failure is one, so roll back only once those runs have ended.
- `ProviderError::Connect`: a connection never made (refused, DNS, TLS handshake, connect timeout), so the request never went out; its error event's `kind` is `connect`, and a scripted turn can fail with `{"type": "connect", "message"}`.
- A call that failed before costing anything (`Connect`, or an error status before any stream event) settles with a zero usage instead of an unknown one: no `usage` event, `usage_complete` stays true, and a capped budget may retry it. A reset, a read timeout or a failure after output began stays unknown and, under a cap, still ends the run.
- `spec.fallback_models` fails a run over to the next model, in order, once a model has no retry left; the run keeps that model, a resumed run included, and its usage and cost name it. Empty by default.
- `provider_retry` and `model_fallback` events report each retry (`model`, `retry`, `delay_ms`, `error`) and each failover (`from_model`, `to_model`, `error`); the Python client decodes them as `ProviderRetryEvent` and `ModelFallbackEvent`.
- Structured output: `spec.output_schema` (`{name, schema, strict?, description?}`) makes the final answer a JSON object checked against the schema (raw or in a fenced block); the parsed value is `result.structured_output`. `OutputSchema` in `linch_rust` and `linch-core`.
- `spec.structured_output_retries` (default 0) sends a failing answer back to the model with Python's feedback wording, recorded as a `verification` event (`verifier: "output_schema"`, `action: "retry"`); the count is read back on resume, so a crash never grants more.
- Past `structured_output_retries` the run fails: `verification` with `action: "stop"`, an `error` named `StructuredOutputError`, and a `result` of subtype `error` with `structured_error`.
- `stop` runs only on an answer that satisfies the schema and gets the parsed `structured_output` in its request; a `rewrite` is checked again and one that fails the schema fails the run.
- `Agent.run(output_schema=...)`, `run.start` `output_schema` and `RunOptions::output_schema` give one run its own schema; it is stored on the run's first `init` (`InitEvent.output_schema`) so a resume or approve keeps it.
- `InvalidOutputSchema` (code -32031, `RunError::InvalidOutputSchema`): a run's own schema does not compile or its root is not an object; nothing is written.
- `InitEvent.output_schema`: only the first `init` of a run started with its own schema has it; other events are unchanged, but a binary older than this one cannot read the events of a run whose `init` has one.
- Anthropic, OpenAI Chat, OpenAI Responses and Gemini send the output schema in their native structured-output form (`output_config.format`, `response_format`, `text.format`, `responseMimeType` with `responseJsonSchema`); no forced final tool. The shapes follow each vendor's API docs and have not been run against a live API. A fallback model (`spec.fallback_models`) is sent the same schema and its answers are checked the same way.
- `AskUser` (config `ask_user: true`, off by default, as Python's opt-in `AskUserPlugin`): 1 to 4 questions with 2 to 4 options each; a call suspends the run with an `input_request` event (its `questions`) and a `suspended` event of status `awaiting_input`. A subagent's call gets an error instead.
- `Agent.answer(run_id, {tool_use_id: Answer(...)})`, `run.answer` and `Agent::answer` commit each answer as its call's result and continue the run; a request left out is asked again, `Answer.declined(note)` declines. The answer is durable before the run goes on, so a crash never asks twice or answers twice.
- `InvalidAnswer` (code -32032, `RunError::InvalidAnswer`): an answer that names no pending request, misses a question or answers a single-select question with a list; nothing is written.
- `Phase::AwaitingInput` and `InputRequestEvent.questions` are new in the journal; other checkpoints and events are unchanged, but a binary older than this one cannot resume a run waiting for input.
- `Bash` takes `run_in_background`: the command runs on after the call returns its `process_id`; `BashOutput` (read scope) returns what it printed since the last read, waiting up to `wait_ms` for it to end, and `BashKill` (exec scope) kills its process group. At most 4 run at once per session; each is killed after `timeout_ms` (30 minutes by default), when its session closes, when its agent closes and when the server dies, even by SIGKILL.
- A background process does not survive a server restart: `BashOutput` and `BashKill` on an id from before it fail with `no_such_process`, saying so.
- Run leases on Postgres: one server drives a run at a time. Another agent's `resume`, `approve` or `answer` of a run that is driven elsewhere ends with `RunLeased` (code -32033, `StoreError::RunLeased`, `data: {run_id, owner, expires_in_ms}`) and writes nothing. A crashed server's runs are free once their lease runs out (30 s by default; `stores.lease_ttl_ms`, at least 1000, or `PgRunStore::with_lease_ttl`). The driver renews the lease on a timer, one small `UPDATE` per running run every third of the lease, so a long model call keeps it. Memory stores have no leases and are unchanged.
- `RunStore::seize`, `lease_ttl`, `renew` and `release`, defaulted for a store whose claims never expire, and `store::conformance::run_lease_suite` for one whose claims do. A wrapper store must forward them.
- `LeaseLost` (-32022) and `RunLeased` (-32033) in the Python client, both `RunError`s.
- `Agent::released` waits for the lease releases of runs that were dropped; `OpenedAgent::close` waits for them (at most `RELEASE_WAIT`, 5 s), so a `linch-server` that exits normally frees the runs it was driving at once.
- A workflow `agent` call whose run is still leased to a runner that crashed waits until the lease runs out (or the workflow is cancelled) instead of failing.
- Local-server cache usage reads Python's fields: SGLang's top-level
  `cached_tokens` without `prompt_tokens_details`, llama.cpp's
  `cache_read_tokens` and `prompt_cache_hit_tokens` (details or `usage`) and
  `timings.cache_n` when usage reports no cache hit.
- `pricing` in the agent config: rates per model id (`input`, `output`, and
  `cache_read` and `cache_creation`, which default to `input`) that this agent
  prices a model with, replacing the published table for it or adding a model
  the table lacks, such as one a local server serves. Without it a model the
  table does not list costs `None`, as in Python.
- Eval scorer `cost_under` (`budget_usd`): passes when the run's total cost is
  below the budget, unknown when it has none. Python's `cost_under`.
- Eval results report each case's `run_id`, `total_cost_usd`, `usage` and
  `duration_ms` and the same totals for the whole eval; the Markdown report has
  a Cost USD column, as Python's does.
- RPC `eval.run`: runs cases with built-in scorers on an open agent and
  returns the per-case and total pass rate, cost, tokens and duration plus a
  Markdown report; each case's `run_id` is a stored run. It takes a place among
  a tenant's live runs and refuses `agent.close` while it runs.
- RPC `run.report`: the run report (tool calls and timings, usage, context,
  recovery, risk) of a stored run as JSON and Markdown, from `Agent::run_record`
  and its events.
- Python client: `Agent.eval(cases, scorers, include_events=)` and
  `Agent.report(run_id, timeline=)` with the `EvalCase`, `Scorer`, `CaseResult`,
  `EvalReport`, `RunReport` and `RunReportResult` typed dicts; a scorer may also be
  a Python callable, applied to each case result once the cases are done.
- Scheduler: `schedule.create`, `schedule.list`, `schedule.pause`, `schedule.resume` and `schedule.delete` store schedules on an open agent's Postgres database: a cron pattern (five or six fields) in an IANA time zone, daylight saving included, or an interval. Each fire is queued exactly once across any number of workers, and missed fires are caught up in order, as Python Linch's are. Python: `Agent.create_schedule`, `schedules`, `pause_schedule`, `resume_schedule`, `delete_schedule`.
- Heartbeats: a schedule with a `session_id` runs each fire as a new run in that session and skips a fire (counted in `skips`) while its previous fire's job is unfinished or the session has a live run, one suspended for approval or input included. Python: `Agent.heartbeat`, prompted with `CHECK_IN` by default.
- Background runs: `job.enqueue` queues a one-off run; `job.get` and `job.list` report each job's state (`queued`, `running`, `retrying`, `failed`, `done`, `superseded`), attempts, error and run id, for running and ended jobs. Python: `Agent.enqueue`, `job`, `jobs`, `wait_job`, and the `Schedule` and `Job` dicts.
- An agent with memory stores, host tools or callbacks cannot be scheduled or queued: -32040 (`NotBackground`, `data.reason`). Also -32041 `ScheduleNotFound`, -32042 `ScheduleExists`, -32043 `JobNotFound`, -32044 `InvalidSchedule`, all `SchedulerError`s in Python.
- `linch-server --config` takes a `worker` section: the server fires schedules and runs queued jobs on that database, opening each job's stored agent config and checking it against its tenant's allowlists again at every attempt; each background run takes one of the tenant's `max_runs` places. A config may have only a worker, whose tenants need no token. Without the section nothing polls.

Python: `principal=` on `create_schedule`, `heartbeat` and `enqueue`; Python Linch's `RunRequest.principal`.
- A stored agent definition (which holds the config's MCP env and header values) is deleted once no schedule and no unfinished job names it: `linch_worker::prune_definitions`, which a worker runs with the history pruning, from its first poll and every 10 minutes after.
- `linch-worker`: `Timing` (cron in a time zone, or an interval), `create_schedule` with an optional `Cap`, `get_schedule`, `pause_schedule`, `resume_schedule`, `delete_schedule`, `enqueue` with a stored agent definition, `AgentFactory` and `Worker::definitions`, `job`, `jobs` and `prune_history`, and `WorkerConfig::history_retention` (7 days). A job that ends moves to `linch_worker_history` instead of being deleted.

### Fixed

- A provider gate is keyed by the origin (scheme, host, port) of `base_url` plus the key variable, as tenant admission matches it, so `https://x/v1`, `https://x/v1?a` and `https://x/v1//` share one gate instead of each getting its own.

- A named `tool_choice` is checked against each turn's own request (after `before_provider_call`), not only at `agent.open`: on a turn that does not offer the tool (a skill narrowed the tools, tool search deferred it) the request goes out as `auto`, and that turn's `context_build` event has `metadata.tool_choice_dropped`, instead of every provider call failing with a 400. Turns that offer it are unchanged.

- The final tool's call is decided as any call of a batch is: a `pre_tool_use` hook runs on it (a rewrite is the answer, a veto goes back as the call's error result), permission rules apply (a deny goes back the same way; an `Ask` counts as allowed, since nothing runs), and a named final tool's input is checked with the tool's own schema and `Tool::validate` even with no output schema. A veto or deny draws on `structured_output_retries`, so one that never lifts ends the run `failed` rather than looping under a forced `tool_choice`. A `stop` hook's rewrite of a final answer is parsed and checked again (the output schema and the tool), so `structured_output` and `final_text` agree; one that is not a valid object ends the run `failed`. A final call now hears waiting background subagents and peer messages first, as a text answer does, instead of cancelling them: its result says the answer was not taken and carries the notes, and the model calls again.

- `filesystem.memory` shows the file memory as untrusted data: the index is cut to 200 lines and 16 KiB (a note says so), fenced in `<memory-index>` tags under a line saying it is not instructions, with a closing tag in the content broken. On Postgres every session, agent and principal of a namespace shared one `/memories/MEMORY.md`, so a weaker role could plant notes for the others: `filesystem.memory_scope` (`principal` by default, `namespace` for the old shared file; off the wire when absent, in the Python `Filesystem` TypedDict) gives each run's principal `/memories/<key>/MEMORY.md`, `<key>` being 32 hex digits of a SHA-256 of its tenant, user and roles; a run without a principal uses `/memories/MEMORY.md`. This is separation by path, not by permission: the filesystem tools still reach the whole namespace. The hook's policy version is 2 (principal) or 3 (namespace), so deep agents and `memory` agents change their contract and runs created before cannot resume. `ContextBuildRequest` has a `principal` (not sent to RPC callbacks); `Principal::path_key` is public.

- The loop guard also counts what Python does and no longer misses loops. A second count, `max_identical_inputs` (default 10, off the wire at the default, 0 off), ends a run that calls one tool with the same input 10 times among the latest 50 calls whatever the results, so a result that changes every time or two calls that alternate no longer run on to the budget. The repeat count looks at the latest 20 results, so a status read now and then is no loop, and a result moved to a file by large-result offload counts as its content whatever the file's name. A tool that polls is waited on: the same answer `max_idle_turns` times in a row ends the run, and a command that has finished (`BashOutput` marks it `poll_done` in the result's metadata) read again is a repeat at the usual count. A host tool declares `polls: true` (Python `@tool(polls=True)`) and an MCP server lists its polling tools in `polls`. A tenant's forced `tool_choice` (`required`, or a tool that is not the final tool) is refused, at `agent.open` and `run.start`, on an agent with no `max_turns` and no `final_tool_name` (`kind: "tool_choice"`; an output schema alone does not count, as the tool made from it exists only on a provider that cannot take the schema natively).
- Remote execution: a command that prints more than 256 MiB is killed and the call ends `output_limit` with `[output limit reached (256 MiB); the command was killed]` (`BashOutput`: `status: output_limit`), not `interrupted` with "the remote host stopped answering"; it stays `interrupted` when the host does not confirm the kill. Docs: the kill margin is 6 s before a deadline over about 12 s and half of it below that, so a `call_timeout_ms` under about 12 s may make the scheduler drop a remote `Bash` call before the kill is confirmed; `SubprocessHost` commands can read the client's environment through `/proc`.
- Remote execution: a start whose answer is lost, unreadable or late (only an error answer proves the host did not start it) now ends the call `interrupted` with the kill sent, instead of `spawn_failed` and an unwatched command that the model's retry would run twice; a kill answer without an `exit` and any kill after a lost read are `interrupted`, never `timed out`, `aborted` or an exit code; reads that answer next to nothing at once are paced (25 ms) and a command that sends more than 256 MiB is killed; a remote command ends about 6 s before the scheduler's call deadline so its kill fits; the host's refusal text shown to the model is plain text of at most 2 KiB; an agent without `Bash` (`bash: false` or no `workspace`) is no longer refused by schedules, queues and workers because of a remote backend, which a tenant whose first `execution` entry is remote has filled in. `SubprocessHost`: at most 4 MiB of each stream are buffered (the command blocks on its pipe past that), a kill answers with the last 256 KiB per stream and an `exit` only once the shell was reaped, a command nobody reads for `idle_timeout` (120 s) is killed, and one host can serve several connections (the `agent` of each call carries a connection tag).

### Changed

- A worker's history pruning also deletes failed jobs that failed more than `history_retention` ago (`prune_history` counts them); they stayed in `linch_worker_jobs` forever.
- A schedule tool's store or internal failure reaches the model as `the schedule store failed; try again later` (code `store`) instead of the error chain, which could carry the database host and port; the chain is logged with `tracing` (a new `linch-rpc` dependency, already in the tree through `linch-worker`). Refusals the model can act on (a bad cron or time zone, the interval floor, the cap) keep their words.
- A schedule's fire is skipped (counted in `skips`) while an earlier fire's job of the schedule is unfinished, for a schedule without a fixed session too, so a backlog no longer stacks a job per fire; and at the tenant's `max_queued_jobs`, which fires now count against (skipped, never failed). `fire_due_schedules` takes the caps (`&[Cap]`; `&[]` for none) and `Worker::job_caps` gives them to a worker; `linch-server` fills them from its tenants (`BackgroundAgents::job_caps`). A tenant without `max_queued_jobs` keeps uncapped fires.
- Missed schedule fires coalesce: a schedule overdue by several ticks (every worker was down) fires once, counts the other missed ticks in `skips`, and moves its next fire to the first tick after now, where it fired every missed tick, one per poll. This differs from Python Linch on purpose: a day of downtime under a one-minute schedule queued some 1,440 runs, each paid for.
- `enqueue_resume` and `enqueue_approve` give the job the stored agent definition the run's jobs ran with, so a scheduled or queued run that suspended can be continued through the queue (a worker with only a factory, as `linch-server`'s, never took a continuation job without one), and they refuse with `WorkerError::Invalid` when that definition was pruned. The job carries no principal: the run continues for its start principal. A finished job's history row keeps its definition's digest, and `prune_definitions` keeps a definition while a run that is not terminal names it there.
- A run keeps the principal it was started for (`RunRecord::principal`, `NewRun::principal`), and a resume, approve or answer that names none acts for it, where it acted for no principal: leaving the principal out of `run.approve` no longer lets a continuation, or a schedule a `CreateSchedule` call makes in it, escape the start principal's `role` and `unless_role` rules. One that names a principal still acts for that one, checked by tenant admission as `run.start`'s is.
- The permission policy joins the run contract when it is not the default (a mode other than `default`, or any layers, `auto_allow`, path or command fields; the facade's `tasks` and a profile's denied tools add to it), so a run is never resumed or approved under a policy that allows more, or less, than the one it started with (`ContractMismatch`).
- A run cancelled while it plans its tool calls (a hook holding it, or an approve or answer in flight) answers each call with `Tool call aborted` before it ends, instead of leaving the calls unanswered in the session.
- A binary older than this one cannot resume a run a cancel left half done (the `aborting` checkpoint phase); finish such a run with `cancel` or `resume` before rolling back.
- A provider's refusal of a prompt longer than the context window ends a run without `spec.compaction` as `kind` `context_length` with the message `prompt exceeds the model's context window: ...`, where it was `kind` `status` with `provider returned HTTP 400: ...`; `retryable` stays false.
- A binary older than this one cannot resume a run of an agent with `spec.compaction.micro` that crashed during a micro-compaction (the `cleared` checkpoint phase), nor read the events of a run that made a forced compaction (`forced: true`; events refuse unknown fields). Roll back only once those runs have ended.
- `ProviderError::retryable()` is true for an HTTP 408, as Python treats a request timeout.
- With an `after_provider_call` hook attached, an accepted call's receipt and `usage` event are written before the hooks run (`provider_call_stop` included), with `ProviderPending` at the totals that count them; the response is written after them, as before. A crash while such a hook runs no longer loses the paid usage: the resume keeps it in the totals and the budget and calls again under the next delivery attempt, which spends no `provider_retry`. The run costs one more write per accepted call; without an `after_provider_call` hook nothing changes, a `provider_call_stop` observer alone included. `ReconcileError::MissingAssistant` is gone.
- A binary older than this one refuses to resume a run that crashed between such a receipt and its response (an accepted receipt with no `assistant` event, under `provider_pending`): it fails with `MissingAssistant` and resumes nothing wrongly, but an older `linch-worker` marks such a run `failed` (it fails a run on any reconcile error). Roll back only once those runs have been resumed or ended.
- A call that failed with a 500, 502 or 504 before any stream event now settles with an unknown usage instead of a zero one: a gateway can send those after the upstream model already ran and billed. Only a connection never made, a 4xx (408 and 429 included), a 503 or a 529 before any event counts as costing nothing; any other status is unknown too. Under a capped `budget` such a failure is no longer retried, and `usage_complete` is false.

- `stop` feedback (`continue`) reaches the model wrapped in `<system-reminder>`, as Python's does, instead of as bare text.
- A workspace agent now also has `BashOutput` and `BashKill` (`bash: false` leaves all three out), so its run contract changes: a run started under an older binary cannot be resumed.
- `agent.close_session` and `session.close` also kill the session's background `Bash` commands.
- DeepSeek and the vLLM, SGLang and llama.cpp profiles still refuse an output schema, now saying why: no native JSON-schema response format that carries the schema.
- A Postgres resume of a run another server drives is refused (`RunLeased`) instead of taking the run over and paying for its in-flight model call again; it no longer fences the live driver out. `Agent::fail` and a parent resuming its subagents' runs still take a run over, and the driver they fence stops at its next heartbeat with `LeaseLost`.
- `linch_postgres::migrate` serializes on an advisory lock per database and schema (it was sqlx's database-wide one), so two tenants on separate schemas no longer queue behind each other's migrations at startup.
- A journal write fenced by another claim answers -32022 (`LeaseLost`) on the RPC, as a fenced claim does, instead of -32024.
- A run whose stream ends with an error or is dropped releases its Postgres lease (one extra write), so another server can resume it at once; a run that ends or suspends writes nothing more.
- A worker job whose run another process leases waits like a busy session (released with back-off, not counting a failure).
- `store::conformance::run_lease_suite` takes two pairs of handles, `(short, long)`: the steps that expect a live lease without renewing it use the long TTL, so a pause on a loaded machine no longer lets their lease run out; only the renewal and expiry steps wait out the short one.

- An intercept callback without `timeout_ms` (Python `timeout`) no longer times out
  after 30 seconds: it waits until the client answers, the run is cancelled or the
  connection ends, as Python's hooks do. Set `timeout` to bound it.
- `@tool` and `@callback` accept plain functions as well as `async` ones, as Python's tools and
  hooks do; a plain function runs in a worker thread.
- `Edit` accepts an empty `old_string`, as Python's does, instead of refusing it as invalid input: an empty file takes `new_string`; a non-empty file is refused as ambiguous unless `replace_all` is set, which inserts at every position and needs the whole file read.
- The `sandbox` backend refuses to open in a server running as root (any uid 0) or holding effective or ambient capabilities (`ExecutionError::Privileged`).
- The `sandbox` backend reads `/etc` only through an allowlist (loader, name service, TLS, time zone, terminfo, `git` and `python3` files; see the sandbox page) and no longer reads `/opt` unless `read_paths` names it. `/proc` stays readable, by decision.
- The `sandbox` seccomp filter also refuses kernel modules, `kexec`, `reboot`, swap, mounts, `pivot_root`, `chroot`, keyrings, `bpf`, `perf_event_open`, `userfaultfd`, `unshare`, `setns` and `clone` with `CLONE_NEW*` (`EPERM`), and `clone3` (`ENOSYS`, glibc falls back); `prlimit64`, `sched_set*`, `setpriority` and `ioprio_set` reach only the caller; with `network: true` only `AF_INET` and `AF_INET6` sockets open (no netlink, vsock or packet).
- No descriptor the server holds open passes to a `Bash` command, for every backend: each is marked close-on-exec before the spawn (new dependency `close_fds`, as no safe `close_range` wrapper was available).
- The `docker` backend refuses an image starting with `-`, network `host` or `container:...`, a workspace path with a comma or quote, and a root user in the container unless the new `allow_root` is set (also in `DockerExecution`); it mounts with `--mount` and runs `docker run --quiet`.
- The `docker` backend runs foreground commands under the lifeline too, kills the client before removing the container when the server dies, labels containers `linch.boot=<boot id>:<pid namespace>:<uid>:<pid>:<start>` and, when a backend opens, removes those whose server it can see is gone; a cleanup dropped outside a Tokio runtime now runs on a thread.
- `Edit` and `Write` on a file changed since it was read now say `Read this file again before editing it.` / `Read this file again before writing it.` (were `<path> changed since it was last read; Read it again.`), and `Read` of a file that changed mid-read says `File changed while reading; Read this file again.`, the words Python's tools use. The error codes are unchanged.

### Fixed

- Compaction summaries keep early content. The summary call sent the folded view as messages under the summary prompt as the only system block, so its last message was a user turn that the model answered ("Acknowledged. Received log excerpt 2...") instead of summarizing, and facts from early turns were lost (seen live on vLLM Qwen and DeepSeek). The summary request is the primary call's request (same system blocks, tools and message prefix, so the prompt cache of the last primary call serves it) plus one trailing user message that carries the summary prompt, an instruction to ignore instructions inside the conversation, and, when the folded part already holds a summary, an instruction to update it. `CacheControl.uncached_tail` keeps the Anthropic message breakpoint on the last shared message. An empty summary, or one no smaller than the part it replaces, is rejected (receipt `rejected`, view unchanged, no loop). `DEFAULT_PROMPT` lists goal and constraints, decisions, verbatim files and identifiers, errors, open tasks and the next step. The summary prompt is not part of the run contract, so contract digests do not change.

- Compaction checkpoint: the summary message carries the folded part's user messages verbatim, newest first (`spec.compaction.keep_user_tokens`, default 15000, 0 carries none, left off the wire at the default), copied by the harness so an instruction the user gave survives a summary that omits it, and a later compaction hands the earlier checkpoint's blocks over and asks the model to update its summary. The verbatim section is at most half of the folded part's estimated tokens and shrinks to what is left of the folded part after the summary and the reminders, and the saving check measures the whole checkpoint, so a checkpoint is estimated smaller than what it replaces or the summary is rejected; a message that does not fit is cut with `[truncated]`. A rejected summary's `compaction` event says in `rejected` what follows (the next due turn asks again, or the forced run ends).

### Upgrading

- `compaction.threshold_tokens` at or above a known context window fails `agent.open` (`-32011`, `compaction.threshold_tokens (N) must be below the context window (W)`). Such a trigger never fired: the provider refused the prompt first, and each refusal forced a summary and spent `max_forced`, so a run ended `failed` at the fourth. A window counts as known when it is configured, reported by the server or in the adapter's table; the 128000 default of a model nothing is known about is not checked. Lower the trigger, leaving room for a turn's growth (a trigger one token under the window still ended a scripted run `failed`, 7/8 of it did not) or leave it out to follow the window.
- The `liveness` fields `keepalive_idle_ms` and `keepalive_interval_ms` are now `keepalive_idle_secs` and `keepalive_interval_secs` (whole seconds, no alias): a config that still names the `_ms` fields stops the server at startup as an unknown field. Divide by 1000 and round up to at least 1.
- A server's lease owner is its opaque server id (random 8 hex characters, or the config's `server_id`) instead of `linch-rpc`, and the worker's default owner is that id instead of `linch-server-<pid>-<start time>`: a run row written by an earlier build keeps the old owner text until its next claim.
- Postgres migration 7 (`0007_run_principal.sql`) adds `linch_runs.principal` (nullable, no rewrite). Runs started before it have none, so their continuations act for the principal they name, as before. A `RunStore` implementation must store and return the new `principal` field of `NewRun` and `RunRecord` (the conformance suite checks it).
- Runs started before this release by an agent whose permission policy is not the default (including an agent with `tasks` or a profile that denies tools) can no longer be resumed or approved under the new binary: the policy is now in the run contract, so they end with `ContractMismatch`. Let them finish on the old binary, or end them with `cancel`, which does not check the contract. Runs of agents with the default policy keep their contracts.

- Postgres migration 6 adds `linch_runs.lease_holder` and `lease_until` (nullable, no rewrite). As with every migration, a server of an earlier version then refuses to start on that database, and a running one ignores leases: until every server is upgraded, an old one can still take over a run a new one drives (the epoch still fences the loser's writes).

- Worker migrations 5 and 6 (`crates/linch-worker/migrations/0005_scheduler.sql`, `0006_background_principal.sql`) run when a worker, or the first scheduler call on a database, calls `linch_worker::migrate`. Migration 5 adds `linch_worker_agents` and `linch_worker_history` and new nullable or defaulted columns on schedules and jobs (`cron` and `session_id` become nullable); migration 6 adds `principal` to schedules and jobs and two partial indexes on their `agent` column. None rewrites a table. Existing schedules keep their cron pattern, read in UTC, and their fixed session. As with every migration, a worker of an earlier version then refuses to start on that database; one already running does not know the new columns, and one with its own agent for a namespace may take a job queued with a stored definition and run it with that agent, without the job's principal. Upgrade every worker on a database before scheduling there through `linch-server`.
- Worker migration 7 (`0007_history_agent.sql`) adds `agent` to `linch_worker_history` and two partial indexes (no rewrite). History rows written before it have none, so a run whose jobs ended before the upgrade is continued by `enqueue_resume` or `enqueue_approve` without a definition, as before.
- A job that ends now moves to `linch_worker_history` instead of being deleted: code that counted `linch_worker_jobs` rows to see finished work should read `job` or `jobs` (or `linch_worker_history`) instead.
- `linch_worker` API breaks, for code that uses the crate directly:
  - `cancel_schedule` is gone: use `pause_schedule` (keeps the schedule) or `delete_schedule`.
  - `Schedule` has `timing` (`Timing::Cron { pattern, timezone }` or `Timing::Every(Duration)`) instead of `cron: String`; `session_id` is an `Option<SessionId>` (`None`: each fire starts its own session); it gains `agent` and `principal`, so a struct literal must set them (`None` keeps the old behaviour).
  - `RunRequest` gains `agent` and `principal`.
  - `create_schedule(pool, &schedule, cap)` takes a cap (`None` for none) and returns the stored `ScheduleInfo` instead of the first fire time.
- `store::conformance::run_lease_suite(a, b)` is now `run_lease_suite((a, b), (long_a, long_b))`: give a second pair of handles whose lease TTL outlasts any pause (60 s for Postgres).

- Runs of workspace agents started before this release cannot be resumed: the workspace tool list gained `BashOutput` and `BashKill`, so the run contract changed and a resume ends with `ContractMismatch`. Let those runs finish on the old binary, or start new runs.

## 0.1.1 - 2026-11-07

### Fixed

- The task tools (`TaskCreate`, `TaskList`, `TaskGet`, `TaskUpdate`) now belong
  to the session of the root run of the agent tree. A subagent's worker used to
  see an empty list and could not update the coordinator's tasks; it now reads
  and updates them. Unrelated sessions stay apart.
- `TaskStop` on a worker that already finished no longer says it stopped it. The
  reply says the worker already finished and how it ended (`completed`, `failed`
  or `killed`); the worker's status is unchanged, as before.

### Changed

- `linch_tools::task_tools` takes the run store as a second argument:
  `task_tools(store, runs, namespace)`. `TaskCreate::new`, `TaskList::new`,
  `TaskGet::new` and `TaskUpdate::new` take it too, as `new(store, runs,
  namespace)`. Hosts that build the tools themselves pass their `RunStore`; a
  call whose run the store does not know uses its own session.

### Tests

- New tests pin that none of the Python bugs #99 to #108 is present in the Rust
  port (tool scope, file namespaces, secrets kept out of argv, PreToolUse
  actions, Grep cancellation, offload, the roster, worker status and the child
  tool filter).
