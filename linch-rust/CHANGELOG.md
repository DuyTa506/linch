# Changelog

Notable changes to `linch-rust`: the Rust crates under `crates/` and the
`linch-rust` Python client that ships the `linch-server` binary. The Python
package `linch` has its own [changelog](../CHANGELOG.md).

## Unreleased

- A relative path in a call of a workspace tool is judged where the tool resolves it, the workspace, so path rules and the `accept_edits` check name the file the call touches when `project_root` is above or below the workspace; the project root and the workspace being one directory is judged as before. A `project_root` spelled through a symlink is compared in its canonical form, so its rules cover the same files as the real directory.
- The catalog change notice escapes `<`, `>` and `&` in the tool and skill names and descriptions it lists, so a description cannot close the notice's wrapper.
- One provider response holds at most 32 MiB (`MAX_RESPONSE_BYTES`) and 4096 tool calls (`MAX_RESPONSE_TOOL_CALLS`); a stream that passes either fails with `StreamError::ResponseTooLarge` or `TooManyToolCalls`.
- `mcp_urls` entries are matched on origin and path: an entry with a path allows that path and what lies below it, one without allows every path of its origin (`provider_base_urls` still allows its path alone).
- `eval.run` takes at most 256 cases from a tenant (`-32602` beyond that), and its runs are claimed under the server id instead of `linch` (`run_eval_as`).
- A tenant's `agent.open` error for a reliability-policy problem that can involve the operator's rules read with its own (`BuildError::Policy`, marked `data.kind` `policy`: a tool the agent lacks, a cycle, a check that does not compile, a `tool_choice` that defeats the rules) is one fixed sentence when the tenant has a `required_policy`, whatever the wording of the core message, and the original text is logged on the server with the tenant's name; before it matched two phrases of that text. A defect in the text of the tenant's own rule or gate (`BuildError::Invalid`) keeps its message, and the server refuses at start a `required_policy` with such a defect (a blank gate name, a `min_calls` of 0, a cycle) so that message is always the tenant's.
- `ConnectError` has two new variants, `HttpClient` (the HTTP client could not be built) and `ListTooLarge` (the first tool of a listing is over 4 MiB), so an exhaustive `match` on it needs two more arms; `linch-mcp` now depends on `reqwest` directly (0.13.5, the version already locked, one copy) for its own HTTP client; and the text of a JSON-RPC error from a tool call is now `rejected the call (code N): {message}` where it was `rejected the call: {message} (code N)`, so the code survives a cut of the message.
- The MCP streamable HTTP client no longer follows redirects, so the transport's headers stay on the configured URL, and a gateway that answered a same-origin 307 or 308 and worked before now fails the connect with `HTTP 307 Temporary Redirect ... (redirects are not followed; configure the final URL)`: configure the final URL; it still keeps no idle connection (pooling showed 31 to 48 ms stalls in 2 of 9 runs of 50 calls on loopback).
- An MCP server's JSON-RPC error message is cut at 30 000 bytes like result text, and a result keeps at most 8 images in `metadata.images`, with 4 MiB of image data and MIME types in all and a MIME type of at most 255 bytes; an image over a limit is left out, and the note in the text says which limit (`more than 8 images`, `over 4 MiB of image data` or `MIME type over 255 bytes`).
- `Debug` of an MCP HTTP transport shows its URL with the user name, password and query replaced by `redacted`, and the errors of the HTTP transport (a failed connect, a reconnect, the text of a failed tool call) no longer name the URL. A JSON-RPC error message in `ConnectError::Handshake`, `Listen` or `ListTools` is cut at 30 000 bytes like a tool error's, and those three variants no longer have a `source`. `linch-mcp` now depends on `futures` and `sse-stream` (both already locked, one copy each) for the client wrapper.
- An MCP `tools/list` is cut at 1000 tools or 4 MiB of tools as the server sent them (title, output schema, icons and `_meta` count with the name, description and input schema): the tools before the bound are kept in order, the rest are left out and a `tracing` warning (target `linch_mcp`) names the server; a first tool alone over 4 MiB fails the connect (`ConnectError::ListTooLarge`) and a relist then keeps the current tools. `list_changed` relists are limited to one a second, with the notifications in between sharing one relist. `linch-mcp` now depends on `tracing` (already locked).
- The llama.cpp context-window probe stays under the configured `base_url` (`{base}/props`, and `{base}/v1/props` for a base without `/v1`) and no longer asks the parent of a `/v1` base; behind a `/v1` base a stock llama.cpp needs `context_window`.
- A retention pass that is dropped (a worker that stops) closes its pruner-lock connection, which is detached from the pool, so the next pass is no longer reported `contended`.
- A Postgres run claim of a run that has no row ends its transaction before it reads the pruning tombstones, so it no longer needs a second pool connection (a pool of one answered `NotFound` only after the 30 s acquire timeout).
- A lease renewal that arrives after the release is `LeaseLost` and no longer leases the run again; the epoch fence is unchanged.
- A job heartbeat that arrives after the attempt released or failed the job answers `false` and no longer hides the job for a visibility timeout.
- `create` of a run id that retention pruned (its tombstone is still kept) answers `Conflict` (`RunExists`, -32023, `was pruned by retention and its id cannot be used again`), like an existing id, instead of starting a second run, also when the `create` overlaps the pruner's delete of the same id.
- In Rust, `Debug` and serializing a provider `base_url` show its user name, password and query as `redacted`, as for an MCP URL; `to_value_with_secrets` keeps them for the wire. Both the MCP and the provider URL also drop their fragment, and a URL that has no host (`user:token@gw:8443/v1` parses as scheme `user`) is shown as `[redacted]`.
- The usage docs state that name-based bash deny and ask rules are best effort against a shell the engine does not run, list the classes they do not cover, and describe the normalised words form exactly.
- Behind `env`, any word that holds a `=` is an assignment for deny and ask rules, so `env a.b=1 touch M` reaches a `touch *` rule; a `${` followed by a blank or `|` counts as syntax the splitter cannot model (bash 5.3 command substitution).
- A redirection between a wrapper option (`env -u`, `time -o`, `exec -a`) and its argument no longer makes the argument the command for deny and ask rules.
- Bash deny and ask rules always match the words of a segment normalised (blanks collapsed, redirections dropped wherever they appear), so `git push *` covers `git  push origin`, `git<TAB>push origin` and `git 2>&1 push origin`.
- Bash deny and ask rules match each word unquoted while keeping word boundaries, so `git push *` covers `git 'push' origin main` and `rm -rf *` covers `rm '-rf' build`, and a quoted argument stays one word; the docs list `nice`, `nohup`, `setsid`, `timeout` and `xargs` as wrappers a name-based rule does not cover.
- Bash deny and ask rules read the options and `NAME=value` words of `env`, `time`, `exec` and `command` unquoted, accept bundled short options (`env -iu NAME`, `exec -la NAME`) and unique prefixes of long options (`env --uns NAME`), and no longer take the argument of such an option for the command.
- `>&` followed by anything but exactly digits or `-` (`>&2file`, `>&-file`) counts as a redirect to a file, so a narrow allow rule asks for it.
- A `${...}` in double quotes whose body holds `$[` (bash nests the old arithmetic form, so a `}` inside it does not close the expansion) counts as syntax the splitter cannot model.
- The bash file-redirect rule applies to narrow allow rules only: the allow-all rule `*` covers `pytest -q > test.log` again, while `echo` or `git *` allow rules still ask for a command that writes a file; `&>` and `>|` stay unparsed for every rule.
- A bash allow rule no longer covers a command that redirects output to a file (`echo x > file`); descriptor duplication (`2>&1`) and `/dev/null`, `/dev/stdout`, `/dev/stderr` are still covered, and deny and ask rules are unchanged.
- Bash deny and ask rules match the unquoted command word with the arguments as written, so a deny pattern such as `* --force` no longer matches text inside a quoted argument; a `#` after an escaped blank or semicolon is not a comment.
- `function`, `coproc`, an array-element assignment (`a[0]=1`), a descriptor-variable redirection (`{fd}>log`) and a brace expansion (`{rm,-rf}`) in command position count as syntax the splitter cannot model.
- Bash deny and ask rules see the command behind a wrapper option that takes an argument (`env -u NAME`, `env -C DIR`, `time -o FILE`, `time -f FORMAT`, `exec -a NAME`) and no longer match the argument itself or `command -v NAME`; `env -S` counts as syntax the splitter cannot model.
- Bash deny and ask rules also see a command behind a quoted or escaped `env`, `command`, `exec`, `builtin`, `time` or reserved word (`\env rm`, `"time" rm`).
- A `${...}` inside double quotes whose body holds a quote, a backslash or a nested `${` counts as syntax the splitter cannot model, so a bash allow rule no longer covers the commands that follow it.
- Bash deny and ask rules also match a command spelled with quotes or escapes (`\rm`, `r""m`) and a command behind leading `NAME=value` words, redirections, reserved words (`if`, `then`, `do`, `!`, `{`) and `time`, `exec`, `command`, `builtin`, `env`; a `$` expansion in command position counts as syntax the splitter cannot model.
- Bash permission rules: `&>`, a `&` after an escaped or quoted `<`/`>`, a `#` comment, here-documents, `>|` and `>&` onto anything but a descriptor count as syntax the splitter cannot model, so allow rules no longer cover them; a backslash inside double quotes is kept before bytes other than `$`, backtick, `"`, `\` and newline.
### Fixed

- **Interrupt payload bound.** An interrupt's payload, which the workflow's stored status keeps, is held to `max_record_bytes` like a record's value (`LimitExceeded`, `bytes in an interrupt payload`).
- **Config errors repeat no input.** A config the server cannot parse is refused with the kind of mistake, what was expected and the line and column, and never a string of the input: serde quoted the value that did not fit and the field it did not know, so a token or DSN in the wrong place reached stderr.
- **Workflow memory per connection.** On a tenant connection, `workflow.step.begin`, `workflow.agent` and `workflow.interrupt` refuse a `name`, `branch` or interrupt `key` over 256 bytes (`-32602`), like the workflow id; a `key` that is only hashed (a step's, an agent call's) and a local connection are not bounded.
- **Counters of calls that journal nothing.** A tenant's workflow keeps counters for at most 10,000 distinct call keys per drive (`MAX_CALL_KEYS`, or `max_records` if larger; `WorkflowOptions::max_call_keys` in `linch-ext`, `None` by default), refusing a call with a new key past it (`-32005`, `kind: call_keys`); failed agent calls and suspended interrupts no longer use up `max_records`. Replays are never refused.
- **Failed steps give their ticket back.** New method `workflow.step.abandon` (capability `workflow_step_abandon`): the Python client's `wf.step` sends it when the step function raised, so a workflow that catches failed steps keeps its places. On a tenant connection a workflow holds at most 10,000 pending step tickets (`MAX_CALL_KEYS`, or `max_records` if larger; `-32005`, `kind: pending_steps`) and they do not count against `max_records`; a local connection has no such cap. A client that never sends it keeps working.
- **Operator system sections and callback rewrites.** A tenant's `before_provider_call` callback that answers `rewrite` no longer removes the operator's `allow.system_sections`: they are put back where the request had them (in the order and with the `cacheable` flag the core laid out, so a rewrite that changes nothing sends the same system), a block repeating their text is dropped, and the rest of the rewritten system is held to 64 KiB (or what the request held beyond the sections, if more).
- **Scheduler calls of a tenant without schedule rights.** `schedule.list`, `schedule.delete`, `schedule.pause`, `schedule.resume`, `job.list` and `job.get` no longer create the queue tables in the database of a tenant with neither `max_schedules` nor `max_queued_jobs`: they read the tables where they exist (reads stay available so the tenant can clean up what it made, also on a worker schema older than the server's) and answer as an empty namespace only where the tables do not exist; a read the older schema cannot answer fails with a generic `-32014` that names no table or migration.
- **Config secrets in the wrong shape.** A token, `cache_salt_secret` or `worker.dsn` given as a bare string where `{"env": ...}` or `{"value": ...}` belongs is refused with `expected an object with `env` or `value``, without the value (it was echoed in the error text).
- **Sandbox IPC.** The `sandbox` seccomp filter refuses System V shared memory, message queue and semaphore calls and POSIX message queue calls with `EPERM`; Landlock does not cover them, and their objects are checked by the server's user id. Programs that need System V IPC stop working in the sandbox: `fakeroot` (it ran before), Perl's `IPC::SysV` users, and databases that take a System V segment at start (PostgreSQL: not tested); use `local` or `docker` for them.

- **Offload paths.** An offloaded tool result is written to `/offload/<session>/<tool>_<call id>_<digest>.txt`, where the digest is of the stored text, so two sessions on a shared backend, or a provider that repeats call ids, no longer overwrite each other's file and no backend call is made to find a free name; a session or call id that is long, empty or holds `/`, `..` or non-ASCII bytes becomes a short segment of readable characters, `~` and a digest, instead of leaving the result inline; the loop guard still stops a model that repeats a call whose result is offloaded after three calls.

- **`Grep` memory and time.** A `Grep` pattern may compile to at most 10 MiB (a larger one is an `invalid_query` that names the way out) and one matcher's lazy DFA cache is capped at 32 MiB, down from the library's 100 MiB and 1000 MiB; the price, measured, is that a 64 KiB line of random `a` and `b` with `[ab]{1,20000}c` takes 16.2 s and 36 MiB instead of 6.3 s and 386 MiB, and a Unicode class repeated 300 times or more (`\w{300}`) is refused. A call now stops with `timed_out` (code, files searched, file reached) after 30 s, checked between files and once per buffer; one regex search over a single very long line cannot be interrupted.

- **`Edit` size and memory.** `Edit` counts the matches and works out the size of its result before it builds anything from them, and refuses a result past 10 MiB (`too_large`, whether it replaces one match or all); an empty `old_string` with `replace_all` is refused (`empty_old_string`); one `Edit` of a 10 MiB file with a one-byte `old_string` no longer holds a list of every match and every line range (255 MiB of extra peak memory before, none beyond the first edit's after).
- A streamed event over the 16 MiB bound and a byte that is not UTF-8 are `stream` errors (`StreamError::EventTooLarge` and `StreamError::NotUtf8`), which are not retried, instead of `transport` errors: the next call would meet the same body, and each default attempt paid for it again. A run that does not retry does not fail over either. Failures of the connection itself stay `transport` and are retried.
- The SSE framer gives its buffer back once a large event has been read (a buffer over 1 MiB that a chunk leaves under a quarter full), and grows it by doubling only up to the 16 MiB bound, so one large event no longer keeps 16 to 32 MiB for the rest of the stream.
- The events a chunk completes before a byte that is not UTF-8, or before the 16 MiB bound, are delivered before the error, so a stream gives the same events and the same error wherever its chunks end (a complete response followed by a bad byte in the same chunk used to fail).
- Error text is cleaned in one order for every error of a provider call, an HTTP error body or a frame inside a stream: the provider key and bearer tokens, then the configured header values and the cache salt, and only then the cut to 500 characters, so a secret that straddles the cut leaves no part of itself behind (the cut used to come first).
- SSE framing reads the body in one pass and no longer depends on `eventsource-stream`: the cost is linear in the bytes whatever the chunk size (the 20 000-delta Anthropic stream decodes in about 12 ms at any chunk size, where it took 190 ms at 256 KiB chunks and 358 ms at 512 KiB; case 6 `rs-kernel`, median per iteration: Anthropic 313 to 25 ms, DeepSeek 221 to 27 ms), a leading byte order mark is dropped instead of panicking, and a body that is not UTF-8 fails the call at the first bad byte.
- One streamed event may hold at most 16 MiB (`sse::MAX_EVENT_BYTES`), an unterminated line included; a stream that passes it fails the call with a `transport` error.
- Error text a provider sends inside a stream (error frames, unknown stop reasons) is cut to 500 characters after scrubbing, like an HTTP error body.

## 0.2.0 - 2026-11-19

0.1.1 was uploaded to PyPI from commit `e102d938` and never tagged; this is the first tagged release. The Python client of this build refuses a server without `server.info` (`IncompatibleServer`), so ship the client and the `linch-server` binary together.

The entries below are condensed to one line per area. The full text of each item is in the git history of this file (`git log -p -- linch-rust/CHANGELOG.md`), and most of the behavior it describes is in the usage and architecture docs. The Upgrading notes are in full.

### Fixed

- **SGLang context overflow and cache salt.** SGLang 0.5.23 answers a too-long prompt with `The input (N tokens) is longer than the model's context length (M tokens).`, which no phrase matched, so the error was `status` and compaction never shortened the prompt; it is now a context overflow. The `sglang` adapter also declares `cache_salt` (SGLang isolates its radix cache by it, checked live), so `allow.cache_isolation` now works on it instead of being refused; the salt does not cover SGLang's LMCache path (issue #37160).
- **Run start durability.** `run.start` answered `{run_id}` before the run existed in Postgres, so a crash right after the answer left a host with an id that does not exist (13 of 991 randomly timed `kill -9` runs found no run, 12 within 50 ms of the answer). The answer now follows the create commit (the run's `init` envelope), as a task of the run, so a start waiting on a `user_prompt_submit` callback holds no request place; `run.resume`, `run.approve` and `run.answer` still answer at once, and a refused start still answers with the refusal as the end of the stream. With the reliab kill harness forced inside 50 ms of the answer (160 kills): 70 acknowledged ids not durable before, 0 after.
- **Fenced writers and interrupted tools.** A session append that lost to a new owner's entries (`conflict: session <id> has 8 entries, expected 4`) reported `RunExists` (-32023); the runner now checks the run's epoch on that conflict and reports `LeaseLost` (-32022), and only a chosen run id already stored stays `RunExists`. A call whose start was durable and whose end a crash lost is still never run again (at most once, not exactly once); its error result now says its effect is unknown, and the stand-in `tool_call_end` carries `error_code` `tool_interrupted`. The pool-timeout message names the resume of a created run.
- **Tool calls and hooks.** A tool call whose final arguments are not a JSON object no longer ends the run `failed`: the call is kept with `input: {}` and the model's text in `ToolUseBlock.raw_input`, and the model reads the error result `invalid JSON arguments for <tool>` (`StreamError::InvalidToolInput` and `NonObjectToolInput` are gone); a panicking hook is caught and handled like a hook error; a `pre_tool_use` or `permission_request` hook with no timeout gives up after 30 s (`HookPoint::default_timeout`, applied at registration, run contract digests unchanged); `Bash`, `BashOutput` and `BashKill` end events carry `status`, `exit_code` or `signal`, `truncated` and `process_id` in `metadata`, failed or not; `provider_retry` and `model_fallback` events are pinned as voiding the text shown before them; the docs list each hook point's default fail mode (guards that fail open by default need `fail_mode: "closed"`).
- **Long tool results.** The filesystem offload (`offload_threshold_tokens`) now stores a structured value as pretty-printed JSON, stores an error as a pointer that keeps its `code` and `details`, and previews at most 2000 bytes; `read_file` returns at most 16384 bytes of one line per call and names the call that continues it (`byte_offset`, with `limit=1`).
- **Compaction.** The trigger measures the view as the larger of the estimate and the latest provider-reported prompt tokens plus what followed (`compaction::Anchor`; `compaction` event `measured_tokens`, read back on resume), so it no longer fires late; a forced summary reads the folded part clipped to a budget and asks again on half as much when the provider refuses it as too long (`compaction` event `clipped_bytes`, `Phase::Cleared` `clip`, strategy `clip` for a last turn too big for the window), so a refused prompt no longer ends the run `failed`; a summary that is rejected, or applied and leaving the view still due, is held after 2 in a row until the view grows by a tenth of the window instead of being bought every turn; an accepted compaction never reports `tokens_after == tokens_before`, and the saving check measures the whole checkpoint; the summary request is the primary call's request plus one trailing user message carrying the summary prompt, a guard against instructions in the conversation and, when the folded part already holds a summary, an instruction to update it (so early content is summarized, not answered, and the primary call's prompt cache serves it; an empty or no-smaller summary is rejected); the checkpoint carries the folded part's user messages verbatim (`spec.compaction.keep_user_tokens`, default 15000).
- **Leases and takeover.** A run's lease is renewed on a connection of its own (`linch_postgres::LeaseLine`, also for the worker's job heartbeat) and its heartbeat is a task of the run, so a busy pool or a client that stops reading no longer lets another server take over a live run and pay again; `RunLeased.owner` is an opaque server id (`server_id` in the config) instead of `"linch-rpc"`; `migrate` reads the applied migrations first and takes the advisory lock only when something is missing, which cuts agent-open latency on a migrated schema.
- **Loop guard, tool choice and gates.** A fix-and-test run whose test prints the same failure after each patch no longer trips `repeated_tool_call` (a succeeding write or exec call with a new input clears the same-result and identical-input counts); a second count, `max_identical_inputs` (default 10), ends a run that calls one tool with the same input 10 times among the latest 50 results; a `required` tool choice left with no tool by a `before_provider_call` hook goes out with no choice, as does a named choice on a turn that does not offer the tool; a completion gate's correction no longer names a tool the turn does not offer; the final tool's call goes through `pre_tool_use` and permission rules like any call.
- **Cost caps and tenant bounds.** A cost cap needs a price: `agent.open` with `budget.max_cost_usd` fails (`-32011`) for the primary model or a `fallback_models` entry with no price, and `workflow.start` refuses an unpriced `max_cost_usd` (`-32011`, `WorkflowError::BudgetUnpriced` `-32046`); tenant admission refuses a spec with neither `max_turns` nor a `budget` (`-32004`, `kind: run_bound`); `spec.call_timeout_ms` under 100 fails `agent.open`; the tool cache key carries the run's principal and `tool_cache.quota` left the run contract.
- **Principals and secrets.** `exec.start` carries the run's `principal`; `workflow.start` takes a `principal`, stored with the journal (migration 2 of linch-ext); credential-named request headers are scrubbed from provider error text at any length and `Debug` of `Schedule` and `RunRequest` hides the agent definition.
- **Provider questions and capabilities.** A tenant's `base_url` can no longer steer the server's key to another path of an allowed origin (`provider_base_urls` match the path); `provider.capabilities` is keyless and window probes read at most 64 KiB; `provider.models` and `provider.model` errors carry one fixed message per `ProviderRequestFailed.kind` (`unreachable`, `status`, `invalid_request`, `other`), are limited to 10 calls a minute per tenant (`-32005`, `kind` `provider_calls`) and report a cut list as `truncated`; `ProviderCapabilities.native_output_schema` became `output_schema: "native" | "final_tool"`; a provider gate is keyed by the origin of `base_url` plus the key variable; every agent open no longer builds its own HTTP client (agents opened with one `PgPools` share one per settings; `PgPools::http_clients`, `RequestOptions::shared_clients`); `spec.temperature` exists (0 to 2, `anthropic` at most 1); vLLM `reasoning_effort` `high` and `max` are sent as `xhigh`; DeepSeek keeps `total_cost_usd` `None` without `pricing`, on purpose; `init.tools` lists the final tool a run made from its output schema.
- **Server, connections and processes.** `liveness.keepalive_idle_ms` and `keepalive_interval_ms` became `keepalive_idle_secs` and `keepalive_interval_secs` (whole seconds, no alias); a silent WebSocket is dropped at `pong_timeout_ms`, not at the next ping tick; the server sets TCP keepalive and a user timeout and pings each WebSocket so a vanished client frees its place; a run holds at most 16 waiting steers (`SteerQueueFull`, `-32005`, `kind` `steers`); `SubprocessHost` commands and MCP stdio servers no longer outlive a `SIGKILLed` client or `linch-server` (a per-process watchdog kills the process group); `linch-server` writes `tracing` records to stderr (`LINCH_LOG`, or `RUST_LOG`).
- **Workflows, scheduler and events.** A workflow answer applies only to the question that was asked (a changed payload asks again and journals an `interrupt_stale` event); `workflow.start` with `resume` on an empty journal is refused (`-32049`, `WorkflowNoJournal`); a job that gave up after 5 attempts reads `failures: 5`; `schedule_fire` events are written `ignorable: true`; pruning keeps the definition a non-terminal run's continuation needs; the tool cache retries a failed clear once before it stops caching for the agent; remote execution ends a command over 256 MiB as `output_limit` and a lost start answer as `interrupted`; `filesystem.memory` is fenced as untrusted data (200 lines, 16 KiB).
- **Docs and tests.** Provider docs state Anthropic's sampling-parameter rule for Sonnet 5.5 and vLLM's `request.extra_body.reasoning_effort`; the usage and architecture pages and the `build-agent-with-linch-rust` skill match the code (23 hook points, error code table, migrations `0007` and `0009`, event and scheduler notes, memory recall times); Postgres test schemas carry the process id, lease and job tests use margins that survive a 2 s commit stall, and the macOS `Bash` background tests ask `ps`.
- **Memory per session.** `ToolDefinition.input_schema` is an `Arc<JsonObject>` shared by the registry, the catalog, the logged prefix and every request, so a session no longer deep-copies the tool schemas: 1000 sessions in flight on one agent peak at 268 MB instead of 549 MB (n=3 each); `usage/embedding.md` sizing gains the figure and the `MALLOC_ARENA_MAX=2` knob (207 MB).

### Added

- **Worker threads for a stdio sidecar.** `LINCH_STDIO_THREADS=N` (2 to 256) in the server's environment runs the stdio server on the multi-thread runtime with N workers; unset or `1` keeps the one-thread runtime, and any other value stops the server at startup naming the variable. One thread serves about 700 to 750 turns/s on Postgres; at 2000 concurrent sessions the run wall p50 went 9.7 s (1 thread), 7.4 s (4), 6.4 s (16). Threads cost 1.4x to 2.2x CPU, so the default stays one thread. See `docs/usage/server.md` and `docs/usage/stores.md`.
- **Idempotency key for remote commands.** `exec.start` carries `idempotency_key` (`<run_id>:<tool_use_id>`), derived exactly like a host tool's `ToolContext.idempotency_key`: stable across a resume, unique per tool call, no secret. The Python client hands it to the host as `ExecStart.idempotency_key` so a host can tell a repeated start from a new command; `server.info` lists the capability `exec_idempotency_key`. Additive: an unset key stays off the wire, no run contract digest changes, a client that ignores the field keeps working. The docs state what each backend guarantees after a crash (`local` and `sandbox` foreground commands may outlive the server, `docker` removes the container, `remote` dedupes by key) with a host example.
- **A cap per subagent.** `SubagentDefinition::budget` (frontmatter `max_tokens`, `max_cost_usd`, `warn_ratio` in `.linch/agents/<name>.md`) caps each child run of that definition with the run budget's own meter, units and `BudgetExceededError`: the child's spend still counts against the parent's `budget` (checked first), and a child that reaches its cap ends `failed` with `subagent budget exhausted (N tokens, $X spent)`, which the parent reads as an error result of its `Subagent` call while its run goes on. The cap is per child run (a `SubagentContinue` run starts a fresh one), survives a crash (the resumed child counts its own durable receipts), is checked at build and in `reload_subagents` (a cost cap needs a price), and a malformed frontmatter value skips the file instead of loading it uncapped. Unset, it is off the wire and run contract digests do not change.
- **Usage by model and by subagent.** The `result` event gains `usage_by_model` (serving model id to usage; sums to `total_usage`, so a fallback or a compaction summary on another model shows as its own entry) and `subagent_usage` (child run id to the child's own `total_usage`, `usage_complete`, `usage_by_model`, `total_cost_usd` and the `subagent_type` its call named); the `usage` event gains `cumulative_by_model`, and `Checkpoint` carries `usage_by_model` so a resumed run keeps it. All three are left out when empty (run contract digests and existing events are unchanged; there is no reasoning-token field). Python: `ResultEvent.usage_by_model`, `ResultEvent.subagent_usage` (`SubagentUsage`), `UsageEvent.cumulative_by_model`.
- **`server.info` handshake.** A client learns the server's `server_version`, wire `protocol` (an integer, bumped only for a change an older client would misread), `contract_version` (the run contract digest's version, `linch::CONTRACT_VERSION`; not an input of the digest, pinned with the golden digest), `capabilities` (`cache_isolation`, `provider_info`, `run_steer`, `schedule`, `workflow`), `backends` the build implements and `limits` (`max_message_bytes`, `default_max_runs`) at connect. Every caller gets the same answer, a tenant included: no caps, names, hosts or paths. The Python client calls it when `Server()` or `Server.connect(...)` starts, keeps it on `Server.info` (`ServerInfo`), and refuses a protocol outside the range it speaks (`IncompatibleServer`), a server that has no `server.info` (`IncompatibleServer`, `protocol` `None`) and one that does not answer in 15 s (`HandshakeTimeout`), stopping the child or closing the connection first. Additive: the params are optional and only logged, the result accepts unknown members, no run contract digest changes. A client built before this release works with a server that has it; a client of this release needs a server that has it.
- **Live suites on SGLang.** `LINCH_LIVE_KIND=sglang` (default `vllm`) runs the live suites with that provider kind against the server at `LINCH_TEST_VLLM_URL`; the collected test set is the same with and without it. Their raw-usage checks read the reasoning-token count from either `usage.reasoning_tokens` (SGLang) or `usage.completion_tokens_details.reasoning_tokens` (vLLM). Linch's own `Usage` has no reasoning bucket on any adapter (`completion_tokens` already includes the reasoning tokens), and a test pins that both shapes give the same `Usage`.
- **`tool_interrupted` event.** `tool_use_id` and `tool_name` (Python `ToolInterruptedEvent`), durable and delivered with the stand-in `tool_call_end` of a call a crash interrupted, so a host finds the calls to reconcile with `ToolContext.idempotency_key`; an older client reads it as an unknown event. The docs state at most once and that the built-in `Bash` and the remote execution host carry no idempotency key.
- **Tenant and cache isolation.** `cache_salt_secret` (server config) with `allow.cache_isolation` (per tenant) sends in every request of the tenant's agents the hex HMAC-SHA256 of the tenant's name under the secret, never the name: `cache_salt` to vLLM (0.9.0 and later) and SGLang, `prompt_cache_key` to OpenAI Chat and Responses. It is stable per tenant across runs, servers, workers and restarts, differs per tenant, is not in the config, the stored definition, the run contract, events, errors or `Debug`, and `request.extra_body` cannot replace it; a provider with no such field (DeepSeek, Anthropic, Gemini, llama.cpp) is refused (`NotAllowed`, kind `cache_isolation`), a secret under 16 bytes or none stops the server at startup, and off (the default) no request changes. Library side: `Tenant::with_cache_isolation`, `RequestOptions::cache_salt`, `CacheSalt`. A tenant oracle test pins that another tenant's run, session, workflow, job and schedule ids answer exactly like missing ones; the audit (what keeps tenants apart, the shared queue names and job id sequence, no per-tenant fair share in the worker queue) is in [Server](docs/usage/server.md#what-keeps-tenants-apart).
- **Cache diagnostic.** `monitoring.cache_diagnostic` (default off) streams a `cache_diagnostic` event after each provider call that reports input tokens, saying why the prompt cache read what it did against the run's previous call: `reason` (`model_changed`, `provider_changed`, `ttl_expired`, `system_changed`, `tools_changed`, `compaction`, `prefix_changed`, `low_read` or `none`), `previous_cached`, `cached`, `prompt_tokens` and `first_changed_message`. It hashes each request once per call, keeps only hashes, says nothing under 1024 input tokens (2048 for OpenAI), is stream-only (never stored or replayed) and is not a hook, so the run contract is unchanged; off, nothing is hashed and the stream, log and writes are byte for byte what they were. Python: `CacheDiagnosticEvent`, `AgentConfig["monitoring"]` ([Providers](docs/usage/providers.md#find-out-why-a-cache-missed)).
- **Operations and schema.** `worker.drain_timeout_ms` (default 30000) bounds the worker drain after SIGTERM or SIGINT; `linch::migrate(dsn)`, `linch::check(dsn)`, `linch-server --migrate` and `--check` make the schema a deploy step (exit codes 0 to 4); `agent.open` and a worker's start refuse a database migrated by a newer release (`SchemaNewer`, `-32016`); a pool wait of 30 s fails with `PoolExhausted` and names its remedy; opt-in `worker.retention` deletes ended runs, idle sessions and tombstones in batches; docs for the connection budget and the rolling schema deploy.
- **Workflows over RPC.** `run_workflow(agent, fn, run_id=...)` runs a Python function in the client whose `wf.agent`, `wf.step` and `wf.interrupt` calls the server journals in Postgres so a crash resumes without repeating finished calls; `run_or_resume(agent, run_id, prompt)` starts, returns or continues a run under a chosen id; `linch-ext` gains `WorkflowSession::open_held`, `step_begin`/`step_complete`, `agent_with`, `WorkflowBudget`, `LiveGate` and `JournalStore::hold` for hosts that drive the journal.
- **Providers.** `request.extra_body`, `request.default_headers` and `request.timeout_ms` on every live provider and `chat.*` settings on the Chat Completions providers (a tenant needs `allow.provider_request`); `Provider::capabilities(model)` and model lists; `pricing` per model id; local-server cache usage read as Python does (SGLang, llama.cpp); `spec.provider_retry` with backoff and `Retry-After`, `spec.fallback_models` with `provider_retry` and `model_fallback` events, and `ProviderError::Connect`; `max_provider_concurrency` (`ProviderGate`); `ProviderRequest.context_tail` so the Anthropic cache breakpoint stays on logged blocks; context-length recovery (`ProviderError::ContextLength`).
- **Structured output and tool choice.** `spec.output_schema`, `spec.structured_output_retries` and `Agent.run(output_schema=...)` check the final answer against a schema (`result.structured_output`, `StructuredOutputError`, `InvalidOutputSchema` `-32031`), sent in each provider's native form where it has one; `spec.tool_choice` and `Agent.run(tool_choice=...)` set `auto`, `none`, `required` or a named tool, with the final tool for providers that cannot do both.
- **Agent spec.** Steering (`Agent.steer`, `Run.steer`, `run.steer`, a `steer_received` event); `AgentConfig.task_ledger`; `spec.system` sections and `spec.context_budget`; `spec.loop_guard` (on by default); `spec.policy` for tool prerequisites and completion gates; long-term `memory` (`MemorySave`, `MemorySearch`, `MemoryDelete`, `PgMemoryStore`, migration `0009_memories`) and `filesystem.memory` file memory; `schedule_tools` (`CreateSchedule`, `ListSchedules`, `CancelSchedule`); `AskUser` with `Agent.answer` (`InvalidAnswer` `-32032`, `Phase::AwaitingInput`); cancel of a suspended run (`Agent.cancel`, `Run.cancel`).

### Changed

- **Stdout pipe of a spawned server.** The Python client raises the child's stdout pipe from 64 KiB to 256 KiB after the spawn (`F_SETPIPE_SZ`, Linux only; a refusal such as `fs.pipe-user-pages-soft` keeps 64 KiB and logs at debug). The server joins queued events into lines of up to 64 KiB, so a case 6 burst blocked it 44 times per run; with 256 KiB, 6 (median wall 566 to 535 ms at 2.0 GHz, n=34 and 36). Nothing changes on the wire; the Unix socket and WebSocket transports are not affected.
- **Lints.** Clippy `todo`, `unimplemented`, `unwrap_used`, `panic`, `expect_used` and `let_underscore_must_use` are denied in the crates already clean of them by `#![deny]` in each crate root (see the architecture README).
- **Compaction, providers and hooks.** A provider's refusal of a too-long prompt ends a run without `spec.compaction` as `kind` `context_length`; `ProviderError::retryable()` is true for HTTP 408; a 500, 502 or 504 before any stream event settles with an unknown usage; with an `after_provider_call` hook attached, an accepted call's receipt and `usage` event are written before the hooks run; `stop` feedback reaches the model wrapped in `<system-reminder>`; DeepSeek and the vLLM, SGLang and llama.cpp profiles say why they refuse an output schema.
- **Leases, schedules and the worker.** A Postgres resume of a run another server drives is refused (`RunLeased`) instead of taking it over, a fenced journal write answers `-32022`, a run that ends in an error or is dropped releases its lease, and a worker job whose run is leased elsewhere waits like a busy session; `linch_postgres::migrate` locks per database and schema; a worker's history pruning also deletes failed jobs older than `history_retention`; a schedule tool's store failure reaches the model as `the schedule store failed; try again later`; schedule fires skip while an earlier fire's job is unfinished and missed fires coalesce into one; `enqueue_resume` and `enqueue_approve` carry the stored agent definition; a run keeps the principal it started for; `store::conformance::run_lease_suite` takes `(short, long)` pairs of handles.
- **Cancel and sessions.** A run cancelled while it plans its tool calls answers each call with `Tool call aborted`; `agent.close_session` and `session.close` kill the session's background `Bash` commands.
- **Python client and tools.** An intercept callback without `timeout_ms` waits until the client answers; `@tool` and `@callback` accept plain functions (run in a worker thread); `Edit` accepts an empty `old_string` as Python does; `Edit` and `Write` on a file changed since it was read say `Read this file again before editing it.` or `before writing it.`
- **Sandbox, Docker and descriptors.** The `sandbox` backend refuses a server running as root or holding capabilities (`ExecutionError::Privileged`), reads `/etc` only through an allowlist and no longer reads `/opt` unless `read_paths` names it, and its seccomp filter refuses more calls; no descriptor the server holds open passes to a `Bash` command (new dependency `close_fds`); the `docker` backend refuses an image starting with `-`, network `host` or `container:...`, an odd workspace path and a root user unless `allow_root` is set, and runs foreground commands under the lifeline with labeled containers.
- **Resume and run contract (full text).** An upgrade or a rollback acts on these, so they are kept as written.
  - `Phase::AssistantReceived` records an `after_provider_call` retry in an optional `retry_feedback`, durable with the paid response; checkpoints without one are unchanged, but a binary older than this one cannot resume a run whose checkpoint has one.
  - A run that retried or failed over holds `provider_retry` / `model_fallback` events, which a binary older than this one refuses as an unknown event type: it cannot read or resume such a run (the error is explicit; nothing is resumed wrongly). Since retries are on by default, any run that met a retryable failure is one, so roll back only once those runs have ended.
  - `InitEvent.output_schema`: only the first `init` of a run started with its own schema has it; other events are unchanged, but a binary older than this one cannot read the events of a run whose `init` has one.
  - `Phase::AwaitingInput` and `InputRequestEvent.questions` are new in the journal; other checkpoints and events are unchanged, but a binary older than this one cannot resume a run waiting for input.
  - `filesystem.memory` shows the file memory as untrusted data: the index is cut to 200 lines and 16 KiB (a note says so), fenced in `<memory-index>` tags under a line saying it is not instructions, with a closing tag in the content broken. On Postgres every session, agent and principal of a namespace shared one `/memories/MEMORY.md`, so a weaker role could plant notes for the others: `filesystem.memory_scope` (`principal` by default, `namespace` for the old shared file; off the wire when absent, in the Python `Filesystem` TypedDict) gives each run's principal `/memories/<key>/MEMORY.md`, `<key>` being 32 hex digits of a SHA-256 of its tenant, user and roles; a run without a principal uses `/memories/MEMORY.md`. This is separation by path, not by permission: the filesystem tools still reach the whole namespace. The hook's policy version is 2 (principal) or 3 (namespace), so deep agents and `memory` agents change their contract and runs created before cannot resume. `ContextBuildRequest` has a `principal` (not sent to RPC callbacks); `Principal::path_key` is public.
  - The permission policy joins the run contract when it is not the default (a mode other than `default`, or any layers, `auto_allow`, path or command fields; the facade's `tasks` and a profile's denied tools add to it), so a run is never resumed or approved under a policy that allows more, or less, than the one it started with (`ContractMismatch`).
  - A binary older than this one cannot resume a run a cancel left half done (the `aborting` checkpoint phase); finish such a run with `cancel` or `resume` before rolling back.
  - A binary older than this one cannot resume a run of an agent with `spec.compaction.micro` that crashed during a micro-compaction (the `cleared` checkpoint phase), nor read the events of a run that made a forced compaction (`forced: true`; events refuse unknown fields). Roll back only once those runs have ended.
  - A binary older than this one refuses to resume a run that crashed between such a receipt and its response (an accepted receipt with no `assistant` event, under `provider_pending`): it fails with `MissingAssistant` and resumes nothing wrongly, but an older `linch-worker` marks such a run `failed` (it fails a run on any reconcile error). Roll back only once those runs have been resumed or ended.
  - A workspace agent now also has `BashOutput` and `BashKill` (`bash: false` leaves all three out), so its run contract changes: a run started under an older binary cannot be resumed.
- Docs: `security.md` (English and Vietnamese) describes the trust boundary (the host authenticates users and asserts principals; any connection of a tenant can act on that tenant's runs by id), untrusted tool, MCP and subagent output, overload behaviour (`max_runs`, provider gate, HTTP and pool timeouts, no run deadline) and telemetry content capture (off by default; tool call input is never scrubbed). No behaviour change.

### Upgrading

- A `checkpoint` or `result` or `usage` event that carries the usage breakdowns (`usage_by_model`, `subagent_usage`, `cumulative_by_model`) is refused by a build from before them (strict decoding), so finish or fail such runs before rolling back; a run stored before the upgrade reads and resumes as it was, with the breakdowns empty for the calls it already paid.
- `run.start` (Python `Agent.run`) returns once the run is stored, one Postgres commit later than before (hooks before the create, such as `user_prompt_submit`, run before the answer); an acknowledged run id exists after a crash. The interrupted-tool result text changed (`INTERRUPTED_TOOL_TEXT`), a session append that lost to a new owner is `LeaseLost` where it was `RunExists`, and the pool-timeout message is longer.
- A tool call with invalid final arguments no longer ends the run `failed`: the run goes on and the model reads an error result. A host that matched that failure (`error.message` containing `input is invalid JSON`) should look for the tool result error `invalid JSON arguments for <tool>` instead. An assistant message of a run in progress can now carry `raw_input` on a `tool_use` block; a reader that rejects unknown fields on a message block must accept it.
- A hook at `pre_tool_use` or `permission_request` with no timeout now gives up after 30 s and fails by its `fail_mode` (a block by default). Set `timeout` (Python `callback(..., timeout=...)`, `timeout_ms` on the wire) on one that legitimately waits longer, such as an approval a person gives.
- The run contract of an agent with `filesystem` (a `deep_agent` always has it) changed: `read_file` gained a `byte_offset` parameter and a longer description (the contract holds each tool's schema), and the offload hook's policy version rose from 1 to 2 (an agent whose `offload_threshold_tokens` or `offload_threshold_fraction` is set). A run of an agent with `filesystem` that was stored before the upgrade cannot be resumed or approved under the upgraded binary (`ContractMismatch`): let it finish before upgrading, or end it with `cancel`, which does not check the contract. Agents without `filesystem`, and the digest of a spec with no hooks, are unchanged.
- Each Postgres run store (one per open agent) now keeps one connection of its own beside its pool, opened on the first lease renewal, and a worker keeps one more for its job heartbeat: raise Postgres's `max_connections` by that many (pool maximums are unchanged). A workflow held on a server still takes one more backend outside the pool: N running workflows are N extra connections (a known gap).
- `compaction.threshold_tokens` at or above a known context window fails `agent.open` (`-32011`, `compaction.threshold_tokens (N) must be below the context window (W)`). Such a trigger never fired: the provider refused the prompt first, and each refusal forced a summary and spent `max_forced`, so a run ended `failed` at the fourth. A window counts as known when it is configured, reported by the server or in the adapter's table; the 128000 default of a model nothing is known about is not checked. Lower the trigger, leaving room for a turn's growth (a trigger one token under the window still ended a scripted run `failed`, 7/8 of it did not) or leave it out to follow the window.
- The `liveness` fields `keepalive_idle_ms` and `keepalive_interval_ms` are now `keepalive_idle_secs` and `keepalive_interval_secs` (whole seconds, no alias): a config that still names the `_ms` fields stops the server at startup as an unknown field. Divide by 1000 and round up to at least 1.
- A server's lease owner is its opaque server id (random 8 hex characters, or the config's `server_id`) instead of `linch-rpc`, and the worker's default owner is that id instead of `linch-server-<pid>-<start time>`: a run row written by an earlier build keeps the old owner text until its next claim.
- Postgres migration 7 (`0007_run_principal.sql`) adds `linch_runs.principal` (nullable, no rewrite). Runs started before it have none, so their continuations act for the principal they name, as before. A `RunStore` implementation must store and return the new `principal` field of `NewRun` and `RunRecord` (the conformance suite checks it).
- Runs started before this release by an agent whose permission policy is not the default (including an agent with `tasks` or a profile that denies tools) can no longer be resumed or approved under the new binary: the policy is now in the run contract, so they end with `ContractMismatch`. Let them finish on the old binary, or end them with `cancel`, which does not check the contract. Runs of agents with the default policy keep their contracts.

- Postgres migration 6 adds `linch_runs.lease_holder` and `lease_until` (nullable, no rewrite). As with every migration, a server of an earlier version then refuses to start on that database, and a running one ignores leases: until every server is upgraded, an old one can still take over a run a new one drives (the epoch still fences the loser's writes).

- Worker migrations 5 and 6 (`crates/linch-worker/migrations/0005_scheduler.sql`, `0006_background_principal.sql`) run when a worker, or the first scheduler call on a database, calls `linch_worker::migrate`. Migration 5 adds `linch_worker_agents` and `linch_worker_history` and new nullable or defaulted columns on schedules and jobs (`cron` and `session_id` become nullable); migration 6 adds `principal` to schedules and jobs and two partial indexes on their `agent` column. None rewrites a table. Existing schedules keep their cron pattern, read in UTC, and their fixed session. As with every migration, a worker of an earlier version then refuses to start on that database; one already running does not know the new columns, and one with its own agent for a namespace may take a job queued with a stored definition and run it with that agent, without the job's principal. Upgrade every worker on a database before scheduling there through `linch-server`.
- Worker migration 7 (`0007_history_agent.sql`) adds `agent` to `linch_worker_history` and two partial indexes (no rewrite). History rows written before it have none, so a run whose jobs ended before the upgrade is continued by `enqueue_resume` or `enqueue_approve` without a definition, as before.
- A job that ends now moves to `linch_worker_history` instead of being deleted: code that counted `linch_worker_jobs` rows to see finished work should read `job` or `jobs` (or `linch_worker_history`) instead.
- `linch_worker` API breaks, for code that uses the crate directly:
  - `cancel_schedule` is gone: use `pause_schedule` (keeps the schedule) or `delete_schedule`.
  - `Schedule` has `timing` (`Timing::Cron { pattern, timezone }` or `Timing::Every(Duration)`) instead of `cron: String`; `session_id` is an `Option<SessionId>` (`None`: each fire starts its own session); it gains `agent` and `principal`, so a struct literal must set them (`None` keeps the old behaviour).
  - `RunRequest` gains `agent` and `principal`.
  - `create_schedule(pool, &schedule, cap)` takes a cap (`None` for none) and returns the stored `ScheduleInfo` instead of the first fire time.
- `store::conformance::run_lease_suite(a, b)` is now `run_lease_suite((a, b), (long_a, long_b))`: give a second pair of handles whose lease TTL outlasts any pause (60 s for Postgres).

- Runs of workspace agents started before this release cannot be resumed: the workspace tool list gained `BashOutput` and `BashKill`, so the run contract changed and a resume ends with `ContractMismatch`. Let those runs finish on the old binary, or start new runs.

- `TaskStop` on a worker that already finished no longer says it stopped it. The
  reply says the worker already finished and how it ended (`completed`, `failed`
  or `killed`); the worker's status is unchanged, as before.

### Changed

- `linch_tools::task_tools` takes the run store as a second argument:
  `task_tools(store, runs, namespace)`. `TaskCreate::new`, `TaskList::new`,
  `TaskGet::new` and `TaskUpdate::new` take it too, as `new(store, runs,
  namespace)`. Hosts that build the tools themselves pass their `RunStore`; a
  call whose run the store does not know uses its own session.

### Tests

- New tests pin that none of the Python bugs #99 to #108 is present in the Rust
  port (tool scope, file namespaces, secrets kept out of argv, PreToolUse
  actions, Grep cancellation, offload, the roster, worker status and the child
  tool filter).
